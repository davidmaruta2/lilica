4. THE LOAD-BEARING FINDING: care_space_memberships.user_id references
   auth.users(id) on delete restrict. Membership rows are themselves
   permanently on delete restrict-referenced from records, occurrences,
   assignments, record_links, record_attachments and every mutation-
   receipt table, by deliberate design (historical attribution -
   Phase 7/8's own stated goal).

5. Consequence: auth.users cannot be deleted today without either (a)
   a foreign-key violation, or (b) first destroying every membership
   row that references it, which would cascade into destroying the
   historical attribution on every record, occurrence, link and
   attachment that membership ever touched. Both outcomes are
   forbidden by this same brief.

6. Per the brief's own explicit instruction ("STOP and report the
   required lifecycle design rather than using destructive cascade"),
   I did NOT implement real account/auth-identity deletion. This is
   reported here as the single largest gap against the brief's
   acceptance standard, deliberately, not as an oversight.

7. What ships instead: a real, safe, read-only precheck
   (account_deletion_precheck()) telling the user exactly which named
   care space(s) would block deletion (being that space's sole active
   organiser). Genuinely useful today regardless of how the identity-
   deletion question is eventually resolved.

8. The UI ("Delete account" in the new Privacy & data screen) is
   honest that deletion itself isn't available yet in this version -
   it never shows a fake success message (brief section 43's "must
   not be fake" rule, honored).

9. Real account deletion needs its own, separately-approved schema
   change - likely decoupling care_space_memberships.user_id from a
   hard FK (e.g. on delete set null plus a captured display-name/email
   snapshot at membership-creation time) so history can outlive the
   auth identity that created it. Not made here without explicit
   sign-off; documented in docs/PHASE_18_ARCHITECTURE.md.

10. New migration: supabase/migrations/20260912150000_phase18_privacy_
    export.sql. Two functions only, both security definer, both
    revoked from public/anon, both granted to authenticated only.

11. account_deletion_precheck(): language sql stable. Returns one row
    per care space the caller organises, with a blocking boolean (true
    = sole active organiser there).

12. export_my_data(): language plpgsql stable (read-only). Builds one
    jsonb document: generatedAt, profile (the caller's own profiles
    row), careSpaces (an array, one entry per active membership).

13. Each care space entry includes careSpaceName, yourRole,
    yourGrantedDomains, records, attachments (metadata only),
    recordLinks - every array filtered through
    membership_has_domain_access(), the EXACT SAME function every
    ordinary read already goes through. No second permission system
    was built.

14. A record_links entry is included only when BOTH its source and
    target individually pass that domain check for the caller's own
    membership - proven by pgTAP - mirroring record_links' own read
    RLS policy exactly, so a restricted target never leaks through
    export.

15. Attachments in export are metadata only: id, recordId,
    displayName, mimeType, sizeBytes, uploadStatus, createdAt. Never
    storageObjectPath, never a signed URL, never file bytes.

16. Export delivery needs no cloud storage bucket at all: the client
    calls the read-only RPC, writes the JSON straight to a local file
    (expo-file-system), and hands it to the native share sheet
    (expo-sharing). No server-generated file, no signed URL, no
    durable server-side artifact ever exists to clean up.

17. 17 new pgTAP assertions (245 total across 8 files, up from 228/7):
    sole-organiser precheck blocking/unblocking as role changes, an
    organiser-of-nothing gets an empty precheck, an organiser's export
    covers every domain, a domain-restricted viewer's export shows only
    her granted domain (no bill, no attachment, no link from an
    inaccessible record), no auth-token field ever present, a pending
    (unaccepted) invitee's export is empty.

18. Two real test-writing bugs found and fixed during iteration (not

19. Closed a real, Phase-17-acknowledged gap: document delete/link/
    attachment cleanup used to be a best-effort, fire-and-forget call
    with no retry if it failed offline. New src/documentCleanupQueue.ts
    is a small AsyncStorage-backed durable retry queue, mirroring
    src/recordSync.ts's own established cache pattern.

20. enqueueDocumentCleanup() is awaited as the literal first step of
    App.tsx's removeRecord(), before any network attempt - a durable
    write, so an app kill or offline delete can never forget a record
    still owes cloud cleanup. Idempotent.

21. retryPendingDocumentCleanup() is retried at the same two lifecycle
    points App.tsx already uses for upload retry (app startup, and
    every care-space-records reconciliation pass) - no new background
    daemon. A queue entry clears only once genuinely successful; a
    failure leaves it queued for the next attempt.

22. All operations the queue retries go through the exact same RLS-
    protected RPCs (remove_record_attachment, remove_record_link) that
    already refuse unauthorised access - the queue holds no elevated
    privilege, it is just a durable reminder.

23. 8 new tests (tests/phase18-document-cleanup-queue.test.ts): no-op
    for non-documents, durable-before-network-attempt, idempotent
    double-enqueue, full success clears the queue, a failure leaves it
    queued then succeeds on retry, empty-queue no-op, a never-uploaded
    attachment skips Storage removal but still cleans metadata/links,

27. Device & local data: new src/localData.ts. pendingLocalWork()
    checks three real things before allowing a clear - the record
    cache's outbox (pending mutations), unuploaded attachments, and the
    new cleanup queue (pending cleanup). "Clear data from this device"
    always requires confirmation, and if anything is genuinely pending,
    the warning names exactly what before the user can proceed.

28. clearLocalDataForOwner() removes only this owner's AsyncStorage
    keys (onboarding state, record cache, cleanup queue) and this
    device's local attachment/preview directories. Never touches
    Supabase.

29. After a confirmed clear, the app signs the user out immediately
    (App.tsx's new handlePrivacyClearLocalData), rather than attempting
    a risky live rebuild of in-memory state from a cache just wiped out
    from under it. Next sign-in reconstructs everything cleanly from
    the cloud - a deliberate, safety-first choice, named here rather
    than left implicit.

30. Sign out, Clear data from this device, and Delete account are kept
    as three genuinely distinct actions, never conflated (brief
    sections 17/45): sign out ends the session only; clear-data removes
    local cache/files then signs out; delete-account is precheck-only
    (see findings 4-9 above).
