Source of truth inspected directly (not from memory):

  (record_domain_for_type(), record_sensitivity_for_type(), the
  `records` table's own `record_type`/`record_domain` columns and CHECK

- supabase/migrations/20260911120000_phase15_care_circle.sql
  (membership_has_domain_access(), care_space_domain_grants,

  (record_attachments' own RLS policy)

  (care_space_activity's own RLS policy)

| Record type  | Display label (client) | Permission domain | Source of mapping | Server enforced? | Client enforced? |
|---|---|---|---|---|---|
| `appointment` | Appointment | `general` | `record_domain_for_type()` else-branch | YES (RLS + every mutation RPC) | No independent client filter -- client trusts the server's own read/write result |
| `task` | Task | `general` | else-branch | YES | same |
| `contact` | Contact (Key Contact) | `general` | else-branch | YES | same |
| `update` | Update | `general` | else-branch | YES | same |
| `careNote` | Care note | `health` | explicit `case` | YES | same |
| `bill` | Bill | `financial` | explicit `case` | YES | same |
| `homeMatter` | Home matter | `home` | explicit `case` | YES | same |
| `document` | Document | `documents` | explicit `case` | YES | same |

These are the ONLY eight record types that can ever exist -- confirmed by
the `records` table's own `records_type` CHECK constraint:
`check (record_type in ('appointment', 'task', 'bill', 'homeMatter',
'document', 'contact', 'careNote', 'update'))`. No omitted type: this is
the complete, exhaustive list, not a partial sample.

"Server enforced" means, precisely: `record_domain` is a
`generated always as (record_domain_for_type(record_type)) stored`
column -- Postgres computes and stores it itself on every insert/update;
it is never a value a client can supply or influence. Every read (RLS
`using` clause) and every write (every mutation RPC's own explicit check)
calls `can_access_care_space_records(care_space_id, record_domain,
action)`, which in turn calls `membership_has_domain_access()`.

"Client enforced" is deliberately answered "no independent filter"
everywhere: this app has NO client-side permission logic for records at
all -- the client only ever receives what the server's own RLS-protected
read already permitted, and every write attempt is independently
re-validated server-side regardless of what the UI shows. (The one
UNRELATED client-side gate in this app, `guardMutation`/`isReadOnly`/
`isArchived` from Phase 21C/20D, blocks entitlement/archive states, not
domain permissions -- a different concern entirely, not conflated here.)


################################################################
2. NO SILENT FALLBACK - VERIFIED, NOT ASSUMED
################################################################

Determined: an unknown/new record type CANNOT exist in this schema at
all today. Two independent, structural guarantees, not mere convention:

  (a) `records_type check (record_type in (...8 values...))` -- an
      INSERT or UPDATE attempting any other `record_type` value is
      rejected outright by Postgres itself, before `record_domain_for_
      type()` is even invoked. There is no code path in this schema
      that can produce a record with an unrecognised type.

  (b) `record_domain_for_type()`'s own `else -> 'general'` branch is
      therefore UNREACHABLE by any of the eight real, currently-existing
      record types (each has its own explicit `case`, or falls under the
      else branch by DELIBERATE, verified design -- `appointment`/`task`/
      `contact`/`update` -- not by accident). It exists purely as
      defence-in-depth for a hypothetical FUTURE record type.

  (c) `membership_has_domain_access()` fails CLOSED by construction: it
      is a single `select exists (...)` that requires an explicit
      matching `care_space_domain_grants` row (or organiser role) to
      return true. The absence of a grant is not a special case that
      needs handling -- it is simply the ordinary "no row found" result
      of the same query, which is `false`. Default-deny, not
      default-allow.

CLASSIFICATION: NOT a security defect. This fails closed today, proven
by direct inspection of the actual CHECK constraint and the actual
`exists()` query shape, not inferred from convention.

ONE FORWARD-LOOKING RECOMMENDATION (not a defect, not actioned in this
task): if a NEW record type is ever added, two things must be updated
together: the `records_type` CHECK constraint (or the insert is rejected
outright, failing closed automatically) AND `record_domain_for_type()`'s
own `case` list (or the new type silently defaults to `general` --
i.e., the LEAST sensitive of the five domains, never "all domains" or
"no domain" or an unrestricted one). This is a development-discipline
note for future schema changes, not a defect requiring action now.


################################################################
3. ATTACHMENTS / DOCUMENTS - THE EXACT RULE, SERVER-PROVEN
################################################################

A. A canonical `document` RECORD (`record_type = 'document'`) has its
   OWN `record_domain = 'documents'`, exactly like any other record type.

B. A FILE ATTACHMENT (`record_attachments` row) has NO domain of its
   own at all -- it inherits its PARENT RECORD's domain, always, proven
   directly by its own RLS policy (`supabase/migrations/
   20260912100000_phase16_document_maturity.sql`):

     create policy "members with domain read access can list attachments"
     on public.record_attachments for select to authenticated
     using (
       exists (
         select 1 from public.records r
         where r.id = record_attachments.record_id
           and r.care_space_id = record_attachments.care_space_id
           and public.can_access_care_space_records(
                 record_attachments.care_space_id, r.record_domain, 'read')
       )
     );

   This is an unconditional structural fact, not configurable per file:
   a file attached to a Bills & money record requires `financial`
   access, NOT `documents` access -- regardless of the file's own type
   (a PDF, a photo, anything). A member with ONLY `documents` permission
   cannot see it. Verified directly by reading this exact policy, not
   inferred.

   Confirmed the same rule for every domain named in the brief:
   - A file attached to a Care & health record requires `health` access.
   - A file attached to a Home & car record requires `home` access.
   - A file attached to an Everyday record (`appointment`/`task`/
     `contact`/`update`) requires `general` access.
   - Only a file attached to a genuine `document`-type record requires
     `documents` access specifically -- because THAT record's own domain
     is `documents`.

   The new "Documents" domain description was written precisely to
   reflect this: "Standalone documents, and any files attached to them"
   -- never implying it covers attachments on OTHER-domain records.

SERVER-SIDE ENFORCEMENT: fully proven above via the actual policy text,
not a client-side assumption. Storage bucket access (the private
`document-attachments` bucket) is separately, identically gated -- the
same migration's own Storage policies each call
`can_access_care_space_records(storage_object_care_space_id(name),
'documents', 'write'|'read')` for the bucket-object layer, keyed off the
SAME domain-per-record rule, not a separate one.


################################################################
4. PROJECTION PERMISSIONS - VIEWS, NOT SEPARATE DOMAINS
################################################################

Audited: Home, Calendar, To Do, People, Search, Recent Activity, Care
Summary, Documents. None of these introduces its own permission concept
-- each is a pure client-side or server-read projection built EXCLUSIVELY
from data the server's own RLS has already filtered.

- Home / Calendar / To Do: all read from `state.records`, populated
  exclusively via the `records` table's own RLS-protected select
  (`using (can_access_care_space_records(care_space_id, record_domain,
  'read'))`). A member without `financial` access never receives a bill
  record from the server in the first place -- there is nothing for
  Home/Calendar/To Do to filter, because it was never fetched. Proven:
  if Sarah lacks Bills & money, no bill-type record ever enters
  `state.records` for her session, so it cannot appear in any of these
  three screens' own derived groupings (Overdue/Today/Upcoming, the
  month grid, or Home's own status strip).

- People: Key Contacts (`contact` type, domain `general`) and Care
  Circle membership listing (`list_care_space_members()`, gated by the
  caller's own active membership, not by domain -- membership visibility
  is a different, already-separate concept from record-domain
  visibility) -- neither introduces a new record-domain gate.

- Search (`src/search.ts`): searches only over the ALREADY-FETCHED,
  already-domain-filtered `state.records` array in memory -- it is a
  pure client-side filter over data that was already permission-checked
  server-side before it ever reached the device. A financial record
  Sarah cannot read never exists in the array Search searches.

- Recent Activity (`care_space_activity`): its own RLS policy is
  PER-ROW domain-matched, not blanket:
  `using (can_access_care_space_records(care_space_id, record_domain,
  'read'))`, where `record_domain` is copied onto the activity row AT
  INSERT TIME from the record the event concerns. A bill-related
  activity event (record_domain = 'financial') is invisible to Sarah
  without financial access, proven directly by this policy.

- Care Summary: built entirely from `state.records` +
  `careCircleMembers` + `recentActivity`, all three already
  domain-scoped by the mechanisms above -- introduces no new read path
  of its own.

- Documents (`src/documents.ts`, this session's own new screen): reads
  `record_attachments` directly, governed by the exact policy quoted in
  section 3 above -- a financial document/attachment is invisible to
  Sarah without financial access, by the same parent-record-domain rule.

ONE GENUINE, PRE-EXISTING NUANCE FOUND (not introduced by this task,
not fixed by it -- flagged for an explicit product-owner decision):
the `assignments` table's own SELECT policy
(`supabase/migrations/20260910170000_phase8_occurrence_engine.sql`)
gates on blanket `'general'` domain access, NOT the specific record's
own domain:

  create policy "active organisers can read assignments" on public.assignments
  for select to authenticated using (
    public.can_access_care_space_records(care_space_id, 'general', 'read'));

  In practice, this means a member with `general` read access (which
  every active member has by default unless explicitly denied) could
  read an `assignments` ROW that concerns a financial-domain record or
  occurrence -- i.e., see THAT an assignment exists and who it is
  assigned to (`display_name_snapshot`) -- even without `financial`
  access. It does NOT expose the underlying record's own title or
  content (that stays correctly gated by the `records`/`occurrences`
  tables' own per-domain policies), so this is a narrow metadata-only
  exposure, not a content leak. No current UI surface in this app lists
  raw assignment rows independently of their already-domain-filtered
  parent record, so this is not currently exploitable through any
  existing screen -- but it is a real, structural inconsistency worth an
  explicit decision (tighten the policy to check the actual record's own
  domain, matching every other table's own pattern) before this becomes
  relevant to a future feature. NOT actioned in this task, per its own
  "do not change delete/permission architecture" scope.
