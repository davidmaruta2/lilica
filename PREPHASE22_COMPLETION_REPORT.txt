PART B - CARE-SPACE LIFECYCLE (AUDIT/PROPOSAL ONLY - NOT IMPLEMENTED)
################################################################
Full detail: docs/PHASE_20D_CARE_SPACE_LIFECYCLE_PROPOSAL.md

13. CURRENT CARE-SPACE LIFECYCLE
    Before this session, a care space had exactly two lifecycle
    transitions: creation (onboarding/Add another person) and ending a
    single membership (leave_care_space()/remove_member(), Phase 15) -
    which only ever detaches ONE person from it, never ends the care
    space itself. There was no way to end a care space's own existence at
    all. This is a gap the proposal document identifies as real.

14. CURRENT DATA OWNERSHIP MAP
    care_spaces has two distinct owner concepts, deliberately separate:
    bootstrap_owner_id (who originally created it) and
    commercial_owner_id (Phase 21B, who pays for it). Membership role
    (organiser/contributor/viewer) is a third, independent concept.
    Records/occurrences/assignments/links/attachments/activity all
    reference the care space and its memberships with ON DELETE RESTRICT
    in almost every case (by deliberate historical-attribution design),
    which is precisely why a real deletion capability required the
    detailed cascade documented in Part H below rather than a simple
    schema-level cascade.

15. SCENARIO A - CARE NO LONGER REQUIRED
    Documented in the proposal as the case the remove-supported-person
    feature (Part H) already answers literally, though the proposal
    itself explicitly flags the tension: this brief's own Part B asked for
    audit/proposal only, while a separate, earlier, explicit product-owner
    instruction in this same session ("fix this now... implement this
    now") had already required building real deletion. The proposal names
    this tension rather than silently resolving it either way.

16. SCENARIO B - ORGANISER LEAVING
    An organiser currently cannot "leave" in the ordinary sense -
    leave_care_space() is only for non-organiser roles (Privacy & data's
    "Leave" section explicitly requires `role !== 'organiser'`). An
    organiser must first transfer/share organiser status to someone else,
    or the care space has no path to continued life if they simply stop
    using the app. Proposal recommends an explicit organiser-to-organiser
    handoff flow as a future decision, not yet built.

17. SCENARIO C - SUPPORTED-PERSON REMOVAL REQUEST
    (i.e., Maggie herself asks for her data to be removed.) Currently
    indistinguishable, mechanically, from Scenario A - the same
    delete_care_space() call satisfies it. The proposal flags that this
    may deserve its own distinct consent/audit trail in future (a request
    initiated BY the supported person, evidenced somehow), which is not
    built today - deletion currently only records who the organiser
    caller was, not why.

18. SCENARIO D - SOLE ORGANISER
    delete_care_space() requires the caller to be an ACTIVE organiser -
    any active organiser, not specifically the sole one (mirroring
    remove_member()'s own existing authority level). A sole organiser can
    already delete the space unilaterally today, since there is no
    other organiser to consult - the proposal raises this as a genuine
    product decision (should a sole organiser be able to delete
    unilaterally, or should some other safeguard exist, e.g. a cooling-off
    period) rather than assuming today's shipped behaviour is final.

19. SCENARIO E - MULTIPLE ORGANISERS
    Any active organiser can currently delete the whole care space
    unilaterally, without the other organiser(s) being consulted or
    notified beforehand. The proposal flags this as the single most
    important open product decision from this whole document - it names
    the option of requiring unanimous organiser consent, or at minimum a
    Recent-Activity-style notification, as a real future safeguard, not
    yet built.

20. SCENARIO F - COMMERCIAL OWNER LEAVING
    If the commercial_owner_id's own membership is removed/left, Phase
    21B's transfer_care_space_commercial_ownership() exists for
    deliberate ownership transfer, but nothing today automatically
    reassigns commercial ownership if that member simply leaves without
    transferring first - the proposal flags this as an unresolved edge
    case interacting with Phase 21's entitlement model (a care space could
    end up with no paying owner while still having active organisers).

21. ARCHIVE RECOMMENDATION
    Proposed (not built): a new `ARCHIVED` care_spaces state - hides a
    care space from normal active use (tab/drawer/switcher) without
    deleting any history, reversible by an organiser. Distinguished from
    Delete (irreversible, cascades) and Leave (ends one membership only).
    Requires new schema (a status column + filtering across every existing
    read), explicitly out of this brief's authorised implementation scope.

22. LEAVE RECOMMENDATION
    No change recommended to leave_care_space()'s own existing semantics
    (ends exactly one membership, care space and its data continue for
    everyone else) - already correctly scoped and already implemented
    (Phase 15/18).

23. TRANSFER RECOMMENDATION
    Recommends a future explicit "make someone else the organiser, then
    optionally leave yourself" guided flow (Scenario B), plus reusing
    Phase 21B's existing transfer_care_space_commercial_ownership() as the
    model for a parallel organiser-role transfer RPC. Not built.

24. DELETE/REMOVE RECOMMENDATION
    The proposal recommends the shipped delete_care_space() capability's
    authority level be reconsidered before general release - specifically
    whether ANY active organiser should be sufficient (today's behaviour,
    mirroring remove_member()) or whether deletion specifically (as
    opposed to removing one member) warrants requiring the SOLE organiser,
    or unanimous multi-organiser consent (Scenario E). This is an explicit
    product-owner decision the proposal does not resolve unilaterally.

25. PROPOSED LIFECYCLE STATE MACHINE
    ACTIVE -> ARCHIVED (organiser action, reversible) -> ACTIVE (restore)
    ACTIVE -> DELETED (organiser action, irreversible, cascades - already
      built as delete_care_space(), predating this proposal)
    ARCHIVED -> DELETED (same irreversible action, from either state)
    None of the ARCHIVED transitions exist today - only ACTIVE and the
    already-shipped DELETED terminal state are real.

26. PROPOSED "MANAGE [NAME]'S CARE" DESTINATION
    A single future screen consolidating Archive/Transfer/Delete/Leave
    actions for the active care space, reached from the drawer's
    "[Name]'s care" group (Part A) as a natural sibling to Care
    Summary/Recent Activity. Not built - today these actions remain
    split between Privacy & data (Leave, Remove/Delete) and Care Circle
    (role changes).

27. PERMISSION MODEL RECOMMENDATION
    Recommends distinguishing three permission tiers going forward:
    "any active organiser" (today's Remove/Delete and remove_member()
    level), "sole organiser only" (today's delete_my_account() sole-
    organiser-blocking check), and a new proposed "all active organisers
    must agree" tier for the highest-consequence actions (Scenario E) -
    not built, flagged as a decision.

28. PHASE 18B INTERACTION
    delete_care_space() and delete_my_account() are deliberately
    independent: deleting a care space never touches auth.users or other
    members' own accounts; deleting your OWN account (Phase 18B) already
    correctly blocks if you are the sole organiser of ANY care space -
    unaffected by this session's new capability. No conflict found.

29. PHASE 21 INTERACTION
    delete_care_space() is one of the RPCs Phase 21B deliberately left
    UNGATED by entitlement (alongside leave_care_space()/remove_member()),
    per Phase 21's own "exit actions are never paywalled" principle -
    confirmed still correct and consistent with the new capability.
    Deleting a care space with an active commercial entitlement does not
    refund or cancel any subscription automatically (same store-billing
    limitation already disclosed for account deletion) - the proposal
    flags this as needing its own explicit user-facing disclosure, not
    yet added to the Remove-a-supported-person confirmation copy.

30. LEGAL/PRIVACY DECISIONS REQUIRING EXTERNAL REVIEW
    Whether irreversible deletion (as opposed to archival) is the
    legally-correct default for a "supported person no longer needs
    support" request, versus a data-retention obligation that might apply
    in some jurisdictions; whether a distinct, evidenced consent record is
    needed for Scenario C (the supported person's own removal request)
    specifically. Both flagged, neither resolved - explicitly named as
    needing product/legal review, not an engineering decision.

31. EXACT PRODUCT-OWNER DECISIONS REQUIRED BEFORE IMPLEMENTATION
    (1) Should delete_care_space()'s authority level be raised from "any
    active organiser" to "sole organiser" or "unanimous organiser
    consent"? (2) Should an ARCHIVED state be built at all, or is
    irreversible delete sufficient? (3) Should Scenario C (supported-
    person-initiated removal) be tracked distinctly from Scenario A? (4)
    Should a "Manage [Name]'s care" consolidated screen be built, and
    when? (5) Should deletion disclose the subscription-cancellation
    caveat explicitly in its own confirmation copy? None of these are
    resolved by this report.
