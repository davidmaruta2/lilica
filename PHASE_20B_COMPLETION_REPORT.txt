3. EXISTING ARCHITECTURE DISCOVERED
Traced per section 2 of the brief before writing anything: apply_record_mutation()
is the single funnel for every record create/import/update/delete and
already carries actor_membership_id per mutation via record_mutation_receipts
(an idempotency ledger, not a queryable feed); confirmationHistory is
per-record only, not cross-record; accept_invitation()/remove_member()/
leave_care_space() each already refuse a retry outright before any new
code could run twice; upsert_record_attachment()/mark_attachment_upload_status()
only ever mark a file 'uploaded' once the transfer genuinely completed;
can_access_care_space_records()/membership_has_domain_access() (Phase 15)
are the one shared permission decision reused verbatim for the new
activity table's own RLS.

4. WHETHER ACTIVITY FOUNDATION ALREADY EXISTED
No. Confirmed by direct inspection, not assumed - no true immutable
cross-record activity/event store existed anywhere in the schema.

5. ACTIVITY ARCHITECTURE CHOSEN AND WHY
Smallest correct append-only care_space_activity table, populated by
extending apply_record_mutation()/mark_attachment_upload_status()/
accept_invitation()/remove_member()/leave_care_space() at the exact point
each already knows a genuine transition occurred, rather than a separate
polling/diffing mechanism - reuses this schema's own established
"redefine an RPC, same signature" convention (Phase 15's own precedent)
rather than inventing a new one. A real mistake was caught and corrected
during implementation: the first draft of the apply_record_mutation()
redefinition was based on the ORIGINAL Phase 7 body, which would have
silently regressed Phase 15's own domain-based write-access/assignee-
visibility fix - re-verified against the actual current (Phase-15-redefined)
body before finishing.

6. HISTORICAL/BACKFILL TREATMENT
No backfill. Per the brief's explicit anti-fabrication instruction,
care_space_activity starts genuinely empty - activity is generated only
for events from this migration forward. Nothing was invented to fill in
"what happened before".

7. ACTIVITY EVENTS SUPPORTED
record_created, record_completed, record_reopened, assignment_changed,
date_changed, document_uploaded, member_joined, member_left, member_removed.
Each derived from a truthful before/after comparison of stored data, never
inferred beyond what the data itself proves changed. A plain notes/title/
amount-only edit intentionally produces no event - proven by pgTAP.
Deletion is deliberately not logged this phase (named scope reduction, not
silently absent).

8. ACTIVITY PERMISSION MODEL
Identical to every other table: RLS via can_access_care_space_records(
care_space_id, record_domain, 'read'), the same decision the record itself
would be filtered by. A member with only 'financial' access never sees a
general-domain title in an activity row and vice versa - proven directly
by pgTAP with a real contributor granted only 'general'. Revoked/former
members see nothing for that care space; their own historical events
remain visible to remaining members with truthful attribution
(resolve_membership_identities()'s own established former-member snapshot
logic, reused as-is).

9. ACTIVITY UI/LOCATION
A "Recent activity" link inside People's own Care Circle card (below the
member preview) opens a new, dedicated RecentActivityScreen - grouped by
day, bounded/paginated via "View more". Explicitly NOT a Home preview, per
the brief's own prohibition.

10. ACTIVITY OFFLINE BEHAVIOUR
Server-backed via the existing RPC/auth architecture (no new sync
mechanism invented) - requires connectivity to fetch, exactly like Care
Circle's own member list already does. This limitation is named here, not
silently absent: an offline device sees whatever it last successfully
fetched, and refetches on next connectivity via the same effect pattern
Phase 15's careCircleMembers already established.

11. SEARCH ARCHITECTURE
Purely client-side (src/search.ts) - no schema, no RPC, no vector
database, no embeddings, no AI, no external search service, per the
brief's explicit prohibition. Operates on the exact already-authorised
record array already loaded for the active care space (the same one Home/
Calendar/To Do/People already hold in memory).

12. SEARCH FIELDS/TYPES COVERED
Title, notes, and category-specific visible fields (location, provider,
reference, role, phone, email, amount, responsiblePerson) across all 8
record types, grouped exactly per the brief's own section 17 list
(Appointments/To Do/Bills & renewals/Home & Car/Documents/Contacts/Care
information/Updates). Never searches or exposes an id, uri, storage path,
signed URL, or any other internal/technical field - proven by a unit test.

13. SEARCH PERMISSION MODEL
No separate filtering needed or added - the input array is already exactly
what this device is authorised to have synced (the server's own RLS
already decided that before the data ever reached the client). Scoped to
the CURRENT care space only, never account-wide.

14. SEARCH UI
One SearchButton (new, matching SettingsCogButton's own plain-View icon
technique) in Home's header, next to Settings - inspected against Home/
People/header architecture as the least invasive placement. Opens
SearchScreen: one text field, live grouped results, explicit empty-query
and no-results states, opening the same shared record-detail sheet every
other list already uses.

15. SEARCH OFFLINE BEHAVIOUR
Fully offline-capable, since it never fetches anything - it only reads
records already in memory.

16. CARE SUMMARY ARCHITECTURE
Purely client-side (src/careSummary.ts), a pure projection over records/
Care Circle members/recent activity already loaded elsewhere - no new
schema, no new record type, no duplicate data store.

17. CARE SUMMARY SECTIONS
Needs attention, Coming up, Key contacts, Care Circle, Important care
information, Important documents, Bills & renewals, Home & Car, Recent
activity - only rendered when genuinely non-empty, each bounded to a small
number of items.

18. WHY DISTINCT FROM HOME
Home answers "what needs my attention right now" (an actionable worklist).
Care Summary answers "if I needed to understand this person's care
situation quickly, what would I need to know" - context/continuity/people/
important information, not a reproduction of Home's own status-chip strip
or section classification.

19. CARE SUMMARY PERMISSION MODEL
Same principle as Search - every input array is already correctly scoped
to what the current user is authorised to see; a section with nothing
visible simply never renders, and no "N hidden items" placeholder of any
kind is ever shown (proven directly by a unit test asserting the word
"hidden" never appears in its output).

20. CARE SUMMARY LOCATION
A restrained "Care summary" link beneath People's own "Person being
supported" card - does not replace or crowd the existing bounded Key
Contacts preview, Care Circle summary, or Ask Lilica placement.

21. MULTI-PERSON ISOLATION
Server-side: list_recent_activity()'s own RLS-equivalent filter means a
request for one care space structurally cannot return another's rows -
proven by pgTAP using two genuinely separate care spaces (Beauty/Jackie's
Space). Client-side: a dedicated effect (a previousCareSpaceId ref, firing
only on a genuine id change, never an unrelated re-render) force-closes
Search/Recent Activity/Care Summary the instant the active care space
changes - proven by a dedicated component test reproducing that exact
state machine.

22. FORMER/REVOKED MEMBER BEHAVIOUR
A revoked/former member's own list_recent_activity() call for that care
space returns nothing (no active membership row matches) - proven by
pgTAP. Their historical events remain visible to remaining members,
correctly attributed via the existing resolve_membership_identities()
logic (a live name, or the Phase 18B former_display_name snapshot).
Historical attribution survives; access does not. No access was restored
to anyone.
