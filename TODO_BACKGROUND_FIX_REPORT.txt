1. ROOT CAUSE OF THE PREMATURE BACKGROUND ENDING

Two related but distinct causes, both found by inspection before any
change was made:

  a) LAYOUT (the large cream rectangle): ToDoScreen's ScrollView has
     `contentContainerStyle={styles.content}` with NO `flexGrow`, and
     ScreenBackdrop's own wrapping View has no `flex` at all -- so the
     olive/gradient background's height was exactly the height of its
     OWN CHILDREN (header, subtitle, filter row, and the To Do list
     itself), never the height of the visible viewport. On a short list
     ("Nothing needs doing right now" -- very little content), that
     wrapper ended well above the bottom tab bar. Below it, the plain
     screen background beneath (ToDoScreen's ScrollView has no
     background colour of its own) showed through as a large, accidental
     cream rectangle. This is a content-sized-container bug, not a fixed
     pixel height bug -- confirmed by reading both files directly rather
     than guessing.

  b) DISTRIBUTION (the earlier-reported "large flat block, then a late
     fade"): ScreenBackdrop's shared gradient is `colors={[deep, deep,
     tint]}` at `locations={[0, 0.78, 1]}` over a fixed 620px block --
     flat deep for the first 78% (~483px), with the entire fade
     compressed into the final 22% (~137px). To Do's own header (title +
     subtitle + filter row) carries more content above the fold than
     Home/Calendar/People, so more of that flat 78% stayed visible before
     any fade began, making the transition read as abrupt/late.

3. EXACT LAYOUT/BACKGROUND FIX MADE

  Layout (cause a): `ToDoScreen`'s `content` (contentContainerStyle)
  gained `flexGrow: 1` -- makes the ScrollView's content container fill
  at least the full scroll viewport when actual content is shorter,
  while a genuinely long/scrolling list is completely unaffected
  (flexGrow never shrinks content already taller than the viewport).
  `ScreenBackdrop` gained an opt-in `stretch` prop -- when true, its own
  wrapping View gets `flex: 1`, so it stretches to fill that now-taller
  content container and carries its background colour all the way down
  to wherever the content container ends (i.e. down to the tab bar).
  Only ToDoScreen passes `stretch`; every other screen renders
  byte-identically to before (proven directly in the new test file).

  Distribution (cause b): `ScreenBackdrop` gained an opt-in `stops` prop
  -- an ordered list of {color, location} read directly by
  LinearGradient in place of the default two-stop array. ToDoScreen
  passes a five-stop distribution using ONLY colours already approved
  for this screen: tabAccent.todo.deep (0% and 8% -- top stays
  confidently deep), colors.olive (45% -- a softer olive/sage, already
  in the existing palette), tabAccent.todo.tint (75% -- the existing
  pale sage), colors.oliveSoft (100% -- the existing lightest, near-
  cream tone). No new colour was introduced. Home/Calendar/People pass
  no `stops`, so ScreenBackdrop's original two-stop fade at 0.78 still
  renders for them exactly as before -- proven directly in the new test
  file.

REVISION (same session, after further physical QA)
============================================================

Two further problems reported on-device:
  - the fade still began too early;
  - at the bottom, the gradient stopped and became a visibly separate
    flat cream block instead of continuing smoothly to wherever the
    screen actually ends.

Root cause of the second issue: the `stretch` fix (above) correctly made
the background's flat COLOUR fill the whole viewport, but the
LinearGradient itself still only interpolated across the original fixed
620px block -- beyond that point it was already resolved to one flat
colour, so on a device/content combination taller than 620px there was a
visible seam where "still gradually changing" met "instantly flat".

Fix (same two files, no new files, no colour changes):
  - `ScreenBackdrop`'s `stretch` mode now also sizes the LinearGradient
    itself to the full rendered height of the background (`bottom: 0`)
    instead of the fixed 620px block, so the colour interpolation runs
    the entire way down, however tall the screen actually is -- there is
    no longer a point where it "becomes" flat. Non-stretch screens
    (Home/Calendar/People) are completely unaffected -- still the exact
    original fixed-height block.
  - ToDoScreen's `stops` locations moved later and were spread out
    further: deep now holds through 38% (previously 8%), reaching the
    softer olive/sage by 65% (previously 45%) and the pale tint by 88%
    (previously 75%), with the near-cream tone reserved for the literal
    final stop. Same four colours as before -- no new colour, no colour
    adjusted.

SECOND REVISION (still shows a cut-off on-device)
============================================================

After the fix above, physical QA still showed the gradient stopping
short. Root cause: the first revision made the gradient's OWN height
depend on an absolutely-positioned child (`bottom: 0`) inside a
separately-`flex:1`-stretched parent View -- two nested layout
decisions, and in practice the absolutely-positioned node's resolved
height did not reliably track the parent's flex-resolved height.

Corrected properly: in `stretch` mode, `ScreenBackdrop` now renders the
`LinearGradient` itself as the flex container (`flex: 1`), with no
absolute positioning involved at all -- children render directly inside
it, in an inner View that only carries the horizontal/top padding. There
is now exactly one node whose layout height decides where the colour
interpolation ends, and it is the SAME node the ScrollView's own
`flexGrow: 1` content container stretches -- provably the full available
screen height on any device, any content length, with no fixed pixel box
anywhere in that code path (asserted directly in the test file, which
checks the gradient's own resolved style contains no `height` at all
when stretched). Every non-stretched screen (Home/Calendar/People) took
none of this change -- their gradient is still the exact original
absolutely-positioned, fixed-620px-height block, structurally untouched.

tests/todo-background-fix.test.tsx's "with stretch" test was updated to
match (it now inspects the gradient node itself, not a separate wrapper,
since there is no longer a separate wrapper in stretch mode).

Re-validated: npm run typecheck clean; npm test 46 suites / 466 tests,
zero regressions.

Still NOT committed, NOT pushed -- awaiting physical review of this
corrected version.
