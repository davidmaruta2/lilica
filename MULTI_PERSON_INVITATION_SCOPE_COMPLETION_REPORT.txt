CURRENT ROOT CAUSE
===========================================================================

1. WHY dtm35 CURRENTLY SEES MAGGIE BUT NOT BEN
David invited dtm35@cam.ac.uk by calling invite_member() for Maggie's
care_space ONLY. That created exactly one care_space_invitations row,
scoped to Maggie's care_space_id alone. Nothing in the invite flow ever
let David select Ben too, so no invitation, and therefore no membership,
to Ben's care_space was ever created. dtm35 accepted the one invitation
that existed and got exactly what it granted: Maggie only.

2. CURRENT CARE_SPACE/SUPPORTED-PERSON RELATIONSHIP
supported_people.care_space_id is UNIQUE (enforced by a database
constraint, confirmed by reading the schema directly, not inferred from
the UI). One care_space is, and remains, exactly one supported person.

3. CURRENT MEMBERSHIP SCOPE
care_space_memberships is unique per (user_id, care_space_id). One
membership row is exactly one (person, care space) relationship. There
is no concept anywhere in the schema of a membership spanning multiple
care spaces.

4. CURRENT INVITATION SCOPE
care_space_invitations.care_space_id is a single, not-null column, and
the "one pending invitation per (care_space, email)" unique index is
itself scoped per care_space. An invitation has always been, and
remains, exactly one care space.

("Is that why dtm35 sees Maggie but not Ben" / "does Care Circle span
multiple care spaces": yes to the first, no to the second -- Care Circle
itself is genuinely care-space-specific; CareCircleScreen, list_care_
space_members() and list_care_space_invitations() are all scoped to one
target_care_space_id, confirmed by reading those functions directly.)

ARCHITECTURE
===========================================================================

5. CHOSEN MULTI-PERSON INVITATION ARCHITECTURE
Brief section 8, option A: a lightweight orchestration "bundle" over the
existing, completely unmodified per-care-space primitives. One new
table, care_space_invitation_groups (one row per organiser-facing
invitation ACTION covering 1+ selected supported people, carrying the
ONE human-friendly invite_code and the ONE set of delivery-state
columns). care_space_invitations gains one additive, nullable
invitation_group_id column -- NULL for an ordinary legacy invitation
(completely unchanged), non-null for one child of a group (still an
independently-authoritative row: its own care_space_id, role, domain
grants, status).

6. WHY THIS PRESERVES PER-PERSON SECURITY
invite_member_group() does not reimplement anything -- it calls the
EXISTING invite_member() once per selected care space. Every authority
check (only an active organiser of THAT specific care space may include
it), idempotency rule, and validation invite_member() already enforces
applies identically, per person, with zero duplicated logic. Any
failure other than "already has access" aborts the WHOLE call
(Postgres's own transactional rollback), so nothing partial is ever left
behind. accept_invitation_group()/decline_invitation_group()/revoke_
invitation_group() likewise loop the EXISTING accept_invitation()/
decline_invitation()/revoke_invitation() -- none of the three catches an
exception, so a failure partway through rolls back every child processed
earlier in the same call. Selecting Maggie never implies Ben, proven
directly by pgTAP (item 10 below).

7. LEGACY SINGLE-PERSON COMPATIBILITY
Selecting exactly one person never touches the group machinery at all --
CareCircleScreen calls the plain, unmodified invite_member() directly.
Every pre-existing single-invitation code path (invite_member,
accept_invitation, decline_invitation, revoke_invitation, resolve_
invitation_by_code's legacy branch) is byte-for-byte unchanged in
behaviour. No migration invents additional people for an
already-existing invitation; invitation_group_id is simply NULL for
every row that existed before this migration.

8. GROUP/CODE MODEL
generate_invitation_group_code() reuses the exact same alphabet/length/
shape as the legacy generate_invitation_code(), checked for uniqueness
against BOTH tables so a group code and a legacy invitation's own
(never user-facing) internal code can never collide. resolve_
invitation_by_code() is redefined additively: the already-approved
rate-limit/authentication logic is preserved verbatim; it now checks
the group table FIRST, returning every selected person's name plus a
group_id; if no group matches, it falls through to the completely
unchanged legacy single-invitation lookup.

9. TRANSACTIONAL ACCEPTANCE MODEL
accept_invitation_group() loops the group's still-pending children,
calling the unmodified accept_invitation() for each. No exception
handler wraps the loop, so Postgres's ordinary transactional semantics
make the whole operation atomic for free: if any child fails, every
membership/grant created earlier in the SAME call is rolled back,
including the group's own state -- "Maggie accepted, Ben failed" is
structurally impossible, not merely unlikely. Idempotent: accepting an
already-accepted group raises "This invitation is no longer open" and
creates nothing extra (proven, item 16).

10. REVOKE/DECLINE/EXPIRY MODEL
revoke_invitation_group()/decline_invitation_group() loop the unmodified
revoke_invitation()/decline_invitation() over every pending child, then
mark the group's own status to match -- one coherent user-facing action,
never "Maggie revoked, Ben still pending" left for the organiser to
puzzle over. Expiry is lazy and coherent: resolve_invitation_by_code()
first sweeps every pending child of a matched group for its own expired
expires_at, then marks the GROUP expired only once none of its children
are still pending -- proven directly (item 15) rather than assumed.

ORGANISER UX
===========================================================================

11. SUPPORTED-PERSON SELECTION UI
CareCircleScreen's "Invite someone" form gains a "Who can they help
with?" checkbox section, shown ONLY when the organiser has more than one
eligible person (brief section 17 -- never adding complexity where
there is nothing to select). "They'll only be able to see information
for the people you select" appears beneath it, matching the brief's own
wording.

12. DEFAULT SELECTION
The care space whose own Care Circle screen this is stays preselected
by default; every other eligible person is shown, visible, but NOT
preselected -- proven directly (item under "Client tests" below):
opening the form from Maggie's screen shows Maggie checked and Ben
unchecked.

13. AUTHORITY FILTERING
Only supported people where App.tsx's own locally-known role ===
'organiser' are ever listed (a UX convenience, never the security
boundary). The server independently re-derives and enforces this per
selected care space inside invite_member_group() regardless of what the
client shows or omits -- proven directly (item 11 below): David, who
organises Maggie but only contributes to a third space ("Kate"), cannot
include Kate through this action, and the server rejects the WHOLE
call, not merely that one inclusion.

14. EXISTING-MEMBER/ALREADY-HAS-ACCESS BEHAVIOUR
invite_member_group() reports each selected care space's own outcome
('invited' or 'already_has_access') rather than erroring the whole
call. The client shows this truthfully ("Already has access to: Maggie
-- not included in this invitation") and never submits a duplicate
invitation for an already-active person. If every selected person
already has access, a calm info message appears and no invitation is
created at all.

15. ROLE BEHAVIOUR
One role offered, applied identically to every selected person -- no
per-person role matrix in this version, matching brief section 13
exactly.

16. DOMAIN BEHAVIOUR
One set of selected domains, applied identically to every selected
person via invite_member()'s own existing per-care-space grant
mechanism -- proven independently correct for BOTH Maggie's and Ben's
resulting memberships, not merely for one and inferred for the other
(pgTAP items 8/9 below).

17. INVITATION-CREATED DISPLAY
The panel is now populated directly from the create call's own result
(never a lookup into the currently-active care space's own invitation
list, which could miss the row entirely if the active space wasn't
among those selected). Shows every invited person's name and, when
applicable, who was already excluded because they already had access.

18. EMAIL WORDING
personFirstName became the plural personFirstNames; a one-element array
produces byte-for-byte the same wording proven by the existing test
suite. More than one uses the brief's own preferred phrasing: "David has
invited you to join Lilica to help support Maggie and Ben."

19. SHARE WORDING
The native Share message uses the identical grammatical joining logic
("Maggie" / "Maggie and Ben" / "Maggie, Ben and Jackie") and switches to
"help support X" only when more than one person is involved, otherwise
the unchanged "help with Maggie's care" wording.

list_my_invitations() collapses every still-pending child of the SAME

lets InvitationsScreen show exactly one Accept/Decline pair per

App.tsx's handleAcceptInvitation()/handleDeclineInvitation() now accept

accept_invitation_group() (or the decline equivalents) accordingly. The
shared post-acceptance tail (reconnectCareSpaces() -> integrate
ReconnectedCareSpaces() -> resolveOnboardingStateAfterAcceptingInvitation())
is completely unchanged, extracted into one small helper so neither
entry point duplicates it.

25. RESULTING PERSON SWITCHING

(called by reconnectCareSpaces()) already returns every membership row
an account has, so once accept_invitation_group() creates real

EXISTING person switcher automatically -- proven directly by the
existing, unmodified multi-person.test.tsx suite and confirmed
structurally by reading reconnectCareSpaces()/integrateReconnected
CareSpaces() before making any change.

SECURITY
===========================================================================

26. SERVER AUTHORITY
Every access decision (who may invite for which care space, who may
accept, what role/domains result) is made exclusively by the existing,
unmodified invite_member()/accept_invitation()/membership_has_domain_
access(). The new group functions are pure orchestration -- they call
these, they never reimplement or bypass them.

27. NO GLOBAL-ACCESS BROADENING
Proven directly: adding Jackie as a third supported person and NOT
selecting her for Sarah's invitation leaves Sarah with zero memberships,
zero invitations, and zero visibility of Jackie whatsoever (pgTAP item
10). An existing member's access to one person is never broadened by an
invitation to a different person -- proven by the "existing Maggie
membership + new Ben-only invite" scenario (item 17 below), which
creates exactly one new membership (Ben), never touching Maggie's.

28. IDENTITY ENFORCEMENT
accept_invitation_group() defers its identity check entirely to the
per-child call into the unmodified accept_invitation(), which still
requires the authenticated caller's own email to match invitee_email.
An unrelated authenticated account that resolves a group's code (a
deliberately permissive preview) still cannot accept it -- proven
directly (pgTAP item 12).

29. INVITATION-CODE ENFORCEMENT
The already-approved single-RPC, rate-limited resolve_invitation_by_
code() contract is preserved verbatim (same authentication/threshold/
window logic, same structured result_status discriminator, same
impossibility of a client bypassing the throttle). The client never
sends a list of care-space ids during acceptance -- accept_invitation_
group() takes only a group_id, and the server alone knows which care
spaces that group actually contains.

30. UNSELECTED-PERSON PROOF
pgTAP item 10 (negative selection): after inviting Sarah to Maggie+Ben
only, direct queries confirm zero membership rows, zero invitation rows
of any kind, for Jackie.

31. UNAUTHORISED-ORGANISER PROOF
pgTAP item 11 (authority test): David, a genuine member but only
contributor of a third care space ("Kate"), attempts to include it in a
group invitation alongside Maggie (which he does organise). The ENTIRE
call is rejected server-side ("Only an active organiser can invite
members") and leaves NOTHING behind -- not even an invitation for
Maggie, the space he does organise, proving the client cannot achieve a
partial unauthorised result by mixing an authorised and unauthorised
selection.
