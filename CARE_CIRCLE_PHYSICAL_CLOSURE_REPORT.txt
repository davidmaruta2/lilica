7. 404-VS-200 ROUTING ANALYSIS
   OPTION A (keep the GitHub Pages 404.html fallback for /invite/<id>):
     - Visually correct (right body renders).
     - Real HTTP status is 404 for every such request.
     - Risk: corporate email-security link-scanners (Safe Links-style
       rewriters), some webmail preview/crawler bots, and generic
       "is this link broken" heuristics can judge a link by its status
       code rather than its rendered body -- a 404 on an invitation
       email link is exactly the kind of thing that invites a warning
       banner, a stripped link, or a "this link appears broken" user
       reaction, for a feature whose entire job is to be trusted enough
       to tap.
     - No implementation cost (already built).
   OPTION B (query parameter, /invite/?id=<id>):
     - A real static file (public/invite/index.html) at a real path --
       genuinely returns HTTP 200 on every static host, GitHub Pages or
       otherwise. No path-based server routing needed at all.
     - Email-client reliability: strictly better -- no status-code risk.
     - Mobile-browser behaviour: identical rendering; the id is read
       from location.search instead of location.pathname.
     - Universal Links / App Links (future): unaffected either way --
       Apple/Android path-matching rules match on the URL PATH
       (/invite/*), not the query string, so a constant /invite/ path
       with a varying ?id= is, if anything, a SIMPLER match than a
       varying path segment per invitation.
     - Deep-link parsing (src/invitationLinks.ts): trivial, contained
       change -- one regex added alongside the existing one, old form
       kept as a harmless parsing fallback.
     - Share: unaffected in shape, only the URL string changes.
     - Aesthetics/readability: both are similarly short; not a factor.
     - Implementation complexity: small and fully contained (5 files).
     - Backwards compatibility: nothing in production depends on the
       old format yet (never released), so a clean switch to ONE
       canonical format was possible with no transition period needed;
       old-format parsing was still kept as a defensive fallback.

8. RESULTING ROUTING DECISION
   OPTION B was implemented. This was NOT changed merely because "404
   sounds undesirable" -- it was changed because a 404 is a genuine,
   documented reliability risk specifically for EMAIL links (the exact
   delivery channel this feature depends on), the fix was small and
   fully contained, and it removes the only meaningful downside Option
   A had while keeping every other property identical. Changed
   consistently across: src/invitationLinks.ts (invitationWebUrl +
   parseInvitationIdFromUrl), the deployed send-invitation-email Edge
   Function's joinUrl (redeployed), public/invite/index.html's
   client-side parsing script, the isolated github-pages-hosting
   branch's matching public/invite/index.html and public/404.html
   (committed 5f1466f, pushed, deployed), and every affected automated
   test (tests/invitation-links.test.ts,
   tests/care-circle-invitation-delivery.test.tsx). There is now
   exactly ONE canonical web invitation URL format.
