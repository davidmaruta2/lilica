1. PREVIOUS INCORRECT ARCHITECTURE

Two rejected iterations, both same-day:
  a) Original Phase 18 SettingsMenu: a full-width bottom sheet
     (Modal, justifyContent: flex-end) opening from the bottom
     of the screen, far from the cog that triggered it.
  b) First correction attempt: a small anchored dropdown card
     (260px, top-right near the cog) -- fixed the "far from the
     cog" complaint but not the real problem.
  In BOTH, tapping Account/Care Circle/Privacy & data closed the
  menu/card and swapped the ENTIRE app content area (App.tsx's
  `content` variable) to a separate top-level screen. That
  screen's own Back button then had nowhere to return to except
  App.tsx's normal tab content -- so leaving Care Circle or
  Privacy & data dropped the user on the dashboard, not back in
  Settings. It was a launcher for unrelated pages, not a menu.

2. NEW DRAWER ARCHITECTURE

Settings is now a right-hand application drawer with its own
internal navigation hierarchy. Settings subsections render
within the drawer and do not become ordinary application
screens.

  APP
  |-- currently active tab (Home/Calendar/To Do/People) -- stays
  |   mounted and visible (dimmed) the entire time the drawer is
  |   open; never unmounted, never replaced.
  `-- SETTINGS DRAWER (src/components/SettingsMenu.tsx)
      |-- section: 'menu'        -> the row list
      |-- section: 'account'     -> AccountScreen, real & unchanged
      |-- section: 'careCircle'  -> CareCircleScreen, real & unchanged
      `-- section: 'privacyData' -> PrivacyDataScreen, real & unchanged

  Visual: slides in from the right edge, Animated.timing-driven,
  ~88% of screen width (capped at 480 for tablets), dimmed
  backdrop over the app behind it, safe-area-respecting header
  with a persistent Close, cream/off-white surface and the
  existing borders/spacing language -- no new visual system.

4. INTERNAL NAVIGATION IMPLEMENTATION

  App.tsx owns one state value:
    settingsSection: 'menu' | 'account' | 'careCircle' | 'privacyData'
  plus the existing showSettingsMenu (drawer visible/hidden).

  - A menu row's onPress (SettingsMenu's onOpenAccount/
    onOpenCareCircle/onOpenPrivacyData props) now ONLY calls
    setSettingsSection(x) -- it no longer calls onClose. The
    drawer stays mounted and open; its body swaps.
  - Each embedded screen's onBack now calls
    setSettingsSection('menu') instead of exiting.
  - SettingsMenu's own Close button (and the dimmed backdrop)
    call onClose, which sets showSettingsMenu(false) AND resets
    settingsSection back to 'menu', so the next open always
    starts at the root.
  - This is exactly the smallest-safe-architecture the brief
    asked for (section 19) -- no navigation library, no new
    dependency, a single extra piece of local state plus a
    render-prop (`children`) so SettingsMenu never needs to know
    any of the screens' own data/callbacks.

5. ACCOUNT REUSE

  AccountScreen.tsx is completely unchanged (same file, same
  props, same Phase 14 reminders/quiet-hours logic, same Phase
  18 display-name editing via AuthProvider.saveProfile). The
  ONLY difference from before: App.tsx now renders it as
  SettingsMenu's `children` when settingsSection === 'account',
  with onBack={() => setSettingsSection('menu')} instead of
  onBack={() => setShowAccount(false)}.

6. CARE CIRCLE REUSE

  CareCircleScreen.tsx is completely unchanged -- same
  memberships list, same invitation logic, same role/permission
  display, same Supabase calls (listCareSpaceMembers/
  listCareSpaceInvitations), same refreshCareCircle function.
  Nothing about care_space_memberships, invitations, roles,
  permissions, RLS, or assignment eligibility was touched.

  People's own SEPARATE, pre-existing direct "Manage care
  circle" link (PersonScreen's own chip, independent of the
  Settings cog) is deliberately UNCHANGED -- it still opens
  CareCircleScreen as a full top-level screen via the original
  showCareCircle boolean, with a plain onBack that closes it.
  This was never part of the reported problem (it doesn't route
  through Settings at all), so it was left alone rather than
  folded into the drawer.

  Care Circle therefore now has two possible presentations of
  the SAME screen component: full-screen (from People's direct
  link) and drawer-embedded (from the Settings cog) -- zero
  duplicated business logic between them.

7. PRIVACY & DATA REUSE

  pendingLocalWork()/clearLocalDataForOwner() local-data flow,

  setSettingsSection('menu') instead of setShowPrivacyData(false).

8. UNDERLYING-ROUTE PRESERVATION

  App.tsx's `content` variable (which decides whether Home/
  Calendar/To Do/People/etc. is showing) no longer has ANY
  branch for Account or Privacy & data at all -- those two
  screens ONLY ever render inside the drawer now. The active tab
  is rendered once, underneath the drawer, and the drawer is a
  sibling overlay -- opening any Settings section never touches
  `content`. Proven by tests/settings-navigation.test.tsx's
  parameterised test across all four tabs.

9. SELECTED-PERSON PRESERVATION

  Nothing about the Settings drawer reads or writes
  state.activeCareSpaceId, the person switcher, or any
  onboarding/setup state. The active care space is untouched by
  opening/closing/navigating the drawer -- proven by the same
  test (route+person text asserted unchanged before, during and
  after a full walk through every section).

10. SCROLLING BEHAVIOUR

  Each embedded screen keeps its own existing Screen/ScrollView
  (AccountScreen, CareCircleScreen and PrivacyDataScreen already
  each use the shared `Screen` component's KeyboardAwareScrollView
  -- unchanged). The drawer itself is a fixed-height
  SafeAreaView; its body is either the fixed-height menu list or
  the embedded screen's own already-scrolling content. The
  drawer does not add a second, competing scroll container, and
  the app's bottom tab bar (rendered as a sibling outside the
  drawer entirely) never becomes part of any Settings scroll.
