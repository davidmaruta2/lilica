LILICA - INVITATION CODE RATE-LIMIT SECURITY CORRECTION
Completion report, 14 September 2026

===========================================================================
1. THE EXACT BYPASS DEFECT (GPT/product-owner review finding)
===========================================================================
The prior "final architectural closure" pass implemented rate limiting as
TWO separate client-invoked RPCs: record_invitation_code_attempt() (which
incremented a per-user attempt counter and raised once the threshold was
exceeded) followed by resolve_invitation_by_code() (the actual lookup),
both independently granted EXECUTE to `authenticated`.

Nothing enforced that a client call the first RPC before the second. An
authenticated client could call resolve_invitation_by_code() directly,
skip record_invitation_code_attempt() entirely, and probe codes with no
rate limit applied at all. Client call sequencing is never a security
boundary - this was not genuinely server-enforced rate limiting, only
client-cooperative rate limiting.

===========================================================================
2. FINAL PUBLIC RESOLVER ARCHITECTURE
===========================================================================
Exactly ONE client-callable entry point: resolve_invitation_by_code(text).
It performs, atomically, in one PL/pgSQL function, in this order:
  1. Authentication check (auth.uid()/auth.role()).
  2. Rate-limit accounting - read-then-write the caller's own row in
     invitation_code_attempts (insert first row / roll the window over /
     increment / mark throttled), UNCONDITIONALLY, before any lookup.
  3. Threshold check.
  4. Code normalisation and lookup (only if not throttled).
  5. Returns a single structured row: (result_status, id, care_space_name,
     invited_by_display_name, role, granted_domains).

There is no second function anywhere that can perform step 2 or step 4
independently for a client.

===========================================================================
3. HOW FAILED LOOKUPS NOW PRESERVE RATE-LIMIT ACCOUNTING
===========================================================================
The original defect (found twice this session, in two different forms):
raising an exception from later in the same function rolls back
everything written earlier in that same statement, including the counter
increment. The fix does not raise for any business-level outcome any
more. not_found / inactive / invalid_input / throttled are all RETURNED
as a `result_status` value, never RAISEd. The function always completes
normally, so nothing it wrote earlier in the same call is ever rolled
back. Only a genuine authentication failure still raises - nothing has
been written yet at that point, so there is nothing to lose.

===========================================================================
4. CLIENT-CALLABLE RPCs (after this migration)
===========================================================================
- resolve_invitation_by_code(text) - the sole code-resolution entry
  point. Granted to `authenticated` only.
No other invitation-code-related RPC is granted to `authenticated`.

===========================================================================
5. INTERNAL / NON-CLIENT-CALLABLE HELPERS
===========================================================================
record_invitation_code_attempt() no longer exists at all (DROP FUNCTION,
not merely un-granted - there is no leftover function for a future grant
to accidentally re-expose). invitation_code_attempts itself has RLS
enabled and FORCED with zero policies, so no role can read or write it
directly regardless of function grants; resolve_invitation_by_code() is
SECURITY DEFINER and is the only code path that touches it.

===========================================================================
6. EXECUTE GRANTS (this migration)
===========================================================================
  revoke all on function resolve_invitation_by_code(text) from public;
  revoke all on function resolve_invitation_by_code(text) from anon;
  grant execute on function resolve_invitation_by_code(text) to authenticated;
No grant exists for anon or public. No other function was touched.
