3. PRODUCT PRINCIPLE
================================================================

When someone's 60-day free period ends without an active subscription:

THEIR INFORMATION MUST NOT DISAPPEAR.

Lilica becomes READ-ONLY for commercially gated actions.

The user must still be able to:

- open Lilica;
- view Home;
- view existing records;
- use Calendar;
- use To Do;
- use People;
- search;
- open record details;
- view documents/attachments;
- view Care Circle information;
- export their information;
- access privacy/account controls;
- delete their account;
- leave a care space;
- perform other explicitly ungated safety/account actions already defined
  by Phase 21B.

Do not turn expiry into an account lockout.


================================================================
4. THE UX PROBLEM TO FIX
================================================================

Current Phase 21B behaviour can allow this:

trial expires
→ user taps + Add
→ completes a form
→ presses Save
→ server rejects mutation

Technically secure, but poor UX.

The desired behaviour is:

trial expires
→ Lilica clearly explains that the care information remains available
→ mutation affordances communicate that continued editing/addition requires
  subscription
→ user is directed to the existing Subscription surface
→ user does not waste time completing a form that cannot be saved.


================================================================
5. CENTRAL CLIENT-SIDE ENTITLEMENT STATE
================================================================

Do NOT scatter independent subscription checks throughout dozens of screens.

Inspect the existing Phase 21B entitlement implementation and extend it
cleanly.

There should be a reusable client-side way for UI components to determine:

- whether the current care space is commercially active;
- whether mutations are currently allowed;
- whether the state is trial active;
- subscription active;
- grace/retry;
- expired/revoked;
- unknown/offline as already defined.

Use the existing server-authoritative entitlement source.

Do NOT introduce:

isPaid = true

or any other simplistic local boolean as authority.


================================================================
6. READ-ONLY EXPERIENCE
================================================================

When the current care space is commercially read-only, present a clear,
calm explanation.

Approved meaning:

"Your free period has ended"

"Your information is safe and you can still view everything you've saved."

"Subscribe for £8.99/year to continue adding or making changes."

You may adjust the exact line wrapping/capitalisation to fit the existing
Lilica UI, but do NOT change the meaning or price.

This should feel reassuring and matter-of-fact.

Do NOT use:

- alarming red error screens;
- aggressive sales language;
- countdown pressure;
- fake scarcity;
- repeated modal spam;
- dark patterns.


================================================================
7. WHERE THE READ-ONLY MESSAGE SHOULD LIVE
================================================================

Use judgement based on the existing UI, but the experience must be coherent.

There should be ONE clear, reusable read-only/commercial-state treatment,
rather than every screen inventing its own warning.

A user whose trial has expired should be able to understand reasonably
quickly:

1. why editing is unavailable;
2. that their existing information is safe;
3. that they can continue viewing it;
4. that subscription costs £8.99/year;
5. where to subscribe.

Do not turn every screen into an advertisement.

Prefer a restrained reusable notice/banner/card plus appropriate handling
of mutation controls.

The prominent Home "+ Add" action must not lead an expired user into a form
they cannot save.

10. DO NOT LET USERS COMPLETE UNSAVABLE FORMS
================================================================

→ change ten fields
→ Save
→ failure

Likewise for Add.

If a mutation surface can legitimately remain accessible for another reason,
ensure the user cannot mistake it for a saveable editing workflow.

================================================================
16. COLLABORATORS
================================================================

This is important.

A collaborator does NOT require their own Lilica subscription.

Their ability to mutate a care space depends on BOTH:

1. their existing Care Circle/domain permission; and
2. the commercial entitlement of that care space's commercial owner.

Therefore:

DO NOT show a collaborator messaging implying:

"Your subscription has expired"

if they are not the commercial owner.

Use appropriate wording.

For a collaborator in a care space whose commercial entitlement has expired,
the meaning should instead be along the lines of:

"This care space is currently read-only."

"Existing information is still available, but new information and changes
are paused until the subscription for this care space is active again."

Do not expose another account's billing details.

Do not tell collaborators another person's raw entitlement state.


================================================================
17. WHO SHOULD SEE THE SUBSCRIBE CTA?
================================================================

Inspect the commercial ownership model carefully.

The commercial owner should have a clear route to:

Subscribe for £8.99/year

A non-owning collaborator should NOT be encouraged to purchase an unrelated
personal subscription as though that would unlock this care space.

Their own subscription does not control the owner's care space.

Therefore the collaborator UX must not mislead them.

If the current architecture allows a legitimate ownership-transfer route,
keep that separate and consistent with Phase 21B.

Do not invent a new billing ownership concept.

================================================================
22. SERVER REJECTION REMAINS THE FINAL SAFETY NET
================================================================

Even after implementing proactive client-side blocking:

server-side rejection remains authoritative.

If stale UI state, race conditions, cross-device changes or network timing
allow a mutation attempt to reach the server and the server rejects it for
entitlement reasons:

handle it gracefully.

Do not display:

- raw PostgreSQL errors;
- RPC error codes;
- technical RevenueCat language.

Translate it into the same calm read-only/subscription explanation.

This is important because UI gating can never be considered the security
boundary.
