PART B (invitation delivery) - NOT STARTED, DELIBERATELY
================================================================

Part B of this brief asks for a complete, production-grade invitation
delivery system: secure single-use tokens, real transactional email via
a chosen provider, a Supabase Edge Function holding the sending
credential, deep-link handling (including an unauthenticated-user
journey and an app-not-installed landing page), native Share, resend/
revoke/expiry semantics, and physical email delivery QA to
dtm35@cam.ac.uk.

This was NOT started in this pass because it requires decisions and
external setup that cannot be made or invented unilaterally:

  - An actual transactional-email PROVIDER ACCOUNT for Lilica
    specifically (a Resend/Postmark/SES-type account, its own API key,
    and a verified SENDING DOMAIN via real DNS records) does not exist
    yet for this project. No email can genuinely be sent, and no
    physical delivery QA to dtm35@cam.ac.uk can happen, until one does.
  - A DEEP-LINK SCHEME/domain decision (a custom `lilica://` scheme vs.
    a universal/app link tied to a real domain Lilica controls) affects
    `app.json`, requires platform-specific setup (an
    apple-app-site-association file and Android App Links verification
    for a universal link, or accepting a custom scheme's own real
    limitation of never surviving a fresh App Store install), and has
    not been decided.
  - Whether a small public "not installed" landing page should be built
    at all, and where it would be hosted, is an infrastructure decision
    - Lilica currently has no public website/landing-page
    infrastructure of any kind to build on to build on.

Building the full code architecture speculatively, against a guessed
provider and a guessed domain, risks a large amount of wasted,
unusable work and - per this brief's own section 12 instruction -
inventing credentials or claiming delivery works before it genuinely
does is explicitly what must NOT happen.

Genuinely asking, not stalling: before any Part B code is written,
please confirm:
  1. Which email provider to use (a Resend account already exists for a
     different Luxford Interactive product, Waddl - a SEPARATE Lilica-
     specific account/sending domain is needed, not reuse of that key;
     or name a different provider you'd prefer).
  2. What domain Lilica's invitation emails/deep links should send
     from/use (e.g. a real domain you already control, or none yet).
  3. Whether to build the FULL journey (email + deep link + landing
     page) now, or start with a smaller slice (e.g. real email delivery
     only, with in-app discovery remaining the only "join" path for
     now, deferring deep linking/landing page to its own later pass).

DO NOT COMMIT. DO NOT PUSH. DO NOT START PHASE 22. None of the three has
