## 1. Current Lilica capability inventory (built from the real, current implementation)

Traced from the current repository rather than any older roadmap description, per the brief's own instruction — `AGENTS.md`, `CLAUDE.md`, `README.md`, `docs/PROJECT_BRIEF.md`, `docs/LUMEN_HANDOFF.md`, `docs/CORE_SYSTEM_CONTRACT.md`, `docs/REVISION_LOG.md`, `docs/PHASE_19_ARCHITECTURE.md`/`docs/PHASE_19_QA.md`, and the relevant per-phase architecture docs were all read, plus direct inspection of `src/`, `App.tsx`, `supabase/migrations/`.

- **Welcome/onboarding**: three-slide introduction; Supabase email/password signup with six-digit email verification; six-digit-code password recovery; required organiser display name (`About you`); a Myself/Someone-else fork; multi-person relationship selection and naming; per-person privacy declaration (versioned, timestamped); interest selection (a chip carousel personalising only the initial record-entry order, never a permanent setting); a vertical snapping record-entry stack for the first few records.
- **Supported-person creation**: `bootstrap_supported_people()` transactionally creates a `supported_people` row, one `care_spaces` row, and the creator's own `care_space_memberships` row as organiser, in one idempotent call. Date of birth is deliberately not collected. No structured condition/allergy/dietary/accessibility/likes-dislikes fields exist on the supported-person profile itself — that information, if entered at all, lives only inside free-text `careNote` records.
- **Home**: real-record-only sections (Needs attention/Today/Coming up/Latest), a horizontal "at a glance" status strip (Overdue/Due today/Coming up/Assigned to you/Updates this week), a persistent person-switcher card. No activity feed, no "what changed since I last looked" indicator.
- **Universal Add / record creation-editing**: one category-gateway screen reused for onboarding and everyday use; eight record categories (appointment, task, bill, homeMatter, document, contact, careNote, update); wheel-based date/time pickers; a shared bottom-sheet editor with keyboard-aware scrolling; view/edit separation (`RecordDetail` read-only first, `RecordEditor` behind a real capability check); an `Assigned to` control (Unassigned/You pre-Phase-15, every domain-eligible active member since Phase 15); a "Remind me" toggle (appointment/task/bill/homeMatter); document-only "Related to"/"Does anything need doing?" linking into other records.
- **Calendar**: a month grid plus selected-day list projecting the same `state.records` Home reads — not a separate event store; category-tinted day badges; opens the same record editor. No device-calendar (Apple/Google) sync, import, export, or subscription feed exists.
- **To Do**: open task/bill/homeMatter records grouped Overdue/Today/Upcoming (30-day horizon); All/Mine/Unassigned filters on stable membership identity; completion shares the exact canonical transition the record editor's own Save uses.
- **People**: Supported person header; Key contacts (external, no Lilica account, bounded preview + "View all"); the real Care circle (authenticated members from Phase 15's membership list, summary card, bounded preview, tap-to-detail popup, "Manage" link); an "Ask Lilica" placeholder (not implemented).
- **Key Contacts**: external contacts with name/role/relationship/phone/email — manually entered only. No device-address-book import exists (no `expo-contacts` dependency in `package.json`).
- **Care Circle**: real invitations to Contributor/Viewer roles; explicit per-domain (general/health/financial/home/documents) read/write grants reviewed before sending; server-enforced assignment-visibility; immediate-effect removal/leaving; sole-organiser safety; role change (`change_member_role`) exists server-side but has no UI yet. Member list shows current active members and pending invitations; there is no former-member list surfaced to users (the underlying `membership_status = 'former'` data exists per Phase 18B, but no client screen lists former members), no per-member activity view, and no filtering of records/tasks/events by "show only what member X touched".
- **Invitations**: an invitee-facing `InvitationsScreen` (Accept/Decline), auto-surfacing once per session for pending invitations. No push/email delivery of the invitation itself yet — discovery is in-app only.
- **Reminders (Phase 14)**: local-device-only notifications (no server/push) for appointment/task/bill/homeMatter, with conservative default offsets, quiet hours, a master switch. No collaboration notifications exist (a Care Circle member is never notified that another member added/changed/completed something) — reminders and collaboration notifications are, today, the same (single) notification-delivery mechanism, and only the reminder half is built.
- **Documents**: upload/camera capture; cloud-side attachment metadata and private Storage (Phase 16); typed `record_links` connecting a document to another record; "Does anything need doing?" creates a real linked task; "View document" opens/shares the file. No document-level search, no "Expiring soon"/"Recently added" grouping (a named, deliberate Phase 17 scope reduction), no OCR/text extraction.
- **Settings/Account/Privacy & data**: a right-hand drawer (Account/Care Circle/Privacy & data sections); display-name editing; profile-picture upload (own account only, shown to self and in the Care Circle "You" tile); reminders master switch/quiet hours; a full data-export RPC (`export_my_data()`, domain-filtered, includes real downloaded document files, delivered as `data.json` plus individual file shares — no `.zip`); "Clear data from this device"; "Leave [care space]"; real account deletion (`delete_my_account()`, membership detached/snapshotted as `'former'`, never destroying shared history).
- **Multi-person switching**: an active-person switcher, add-person flow, resume-incomplete-setup flow — unchanged since Phase 6/9.
- **Offline/sync**: a durable AsyncStorage-backed local cache and semantic outbox per Phase 7; a durable document-cleanup retry queue per Phase 18; upload-retry effects for pending attachments; deterministic reconciliation on reconnect. Records/occurrences/assignments/links/attachments all work offline-first with eventual sync; there is no fully offline-first *collaboration* guarantee beyond what the existing sync/conflict model already provides (last-writer-wins-with-compatible-merge, per Phase 7).
- **Search**: no search feature of any kind exists anywhere in the app — not global, not per-screen, not by keyword, not by date range. Confirmed via direct grep of `src/screens/` (zero matches for a search UI) and `package.json` (no search-indexing dependency).
- **Medication**: no dedicated medication record type, no dosage/schedule/administration-tracking/adherence fields. `careNote`'s own onboarding description ("Medication, visits, routines or useful notes") explicitly folds medication into a generic free-text note — confirmed via direct inspection of `src/data/options.ts`.
- **Activity/history**: no cross-record activity feed exists. The closest analogues are per-record `confirmationHistory` (a record's own completion/confirmation timestamps, visible only on that record's own detail view) and the Home "Updates this week" count (a raw count, not a feed of who-did-what). There is no "David added X", "Sarah completed Y" narrative anywhere.

## 3. Carer-needs analysis (why Jointly has each significant capability)

For every significant Jointly capability, the underlying carer need — not the feature checkbox — is assessed against current Lilica behaviour:

- **Messaging**: underlying need is coordinating in real time and having a shared record of what was discussed. Lilica has none of this today; the record model has no comment/thread concept. Families already default to WhatsApp/iMessage/SMS for general chat (as the brief itself notes) — duplicating that would very likely make Lilica worse, not better. But a *narrower* need — attaching a short contextual note to a specific record ("Spoke to GP — prescription ready Friday") — is a genuinely different, much smaller need that Lilica's existing `notes` field on most record types already partially serves, just without a timestamped, attributable, append-only history of who said what and when.
- **Tasks/task lists**: Lilica already solves this via To Do, arguably more cleanly (a real projection sharing one canonical completion transition, rather than a separate module). **Lilica advantage.**
- **Calendar events + recurrence + categories**: Lilica already solves scheduling and recurrence (Phase 8's occurrence/recurrence engine, category-tinted day badges). Google Place location search and DST-safe recurring events are refinements Lilica's own recurrence engine may or may not already handle correctly across DST — not independently verified this phase (flagged as F — needs a small, targeted technical check, not a product decision).
- **Medication tracking**: underlying needs are (a) knowing what someone takes and how, (b) knowing whether it's been administered today, (c) not duplicating a dose across two carers, (d) remembering to reorder/collect a repeat prescription, (e) sharing that information safely. Lilica's `careNote` free-text type solves (a) weakly (no structured dosage/schedule) and does not solve (b)/(c)/(d) at all — there is no administration-tracking or dose-idempotency concept anywhere in the schema. This is a genuine, carer-relevant gap, but implementing (b)/(c) verges into clinical/safety territory the brief explicitly warns against building without an analysis of liability implications (see the Safety/Legal section below).
- **Profile page (condition/likes/dislikes/DOB)**: underlying need is a single place to find "who is this person, what matters to them, what do they need" without hunting through individual records — valuable especially for a new or occasional helper. Lilica deliberately keeps onboarding light and has no equivalent; the need is real but the *timing* (mandatory onboarding vs. an optional, later-fillable profile) is a distinct design decision from whether the capability should exist at all.
- **Notes with attachments**: underlying need is capturing unstructured observations that don't fit a task/appointment/bill. Lilica's `careNote` record type, plus every record's own free-text `notes` field and attachment support, already covers this — **Lilica handles this differently but adequately** for the general case; the narrower "contextual comment on an existing record" need (above) is the part that isn't covered.
- **Contact import**: underlying need is avoiding retyping details already in someone's phone. Genuine convenience win, low product-philosophy risk, but real permission/privacy/complexity cost (see section 7H).
- **"Latest activity at a glance" / member filtering across Events/Notes/Reminders/Tasks**: underlying need is coordination visibility in a multi-person circle — who did what, so effort isn't duplicated and nothing is dropped. This is a genuine, carer-relevant coordination need Lilica does not serve today at all (see section 7A) — arguably the single most carer-relevant gap found in this audit, because Lilica's own Care Circle collaboration model (Phase 15) makes this need *more* acute as more people join a care space, not less.
- **Contingency Plan export**: underlying need is "if I'm suddenly unavailable, can someone else cope" — Lilica's own family-handover and emergency tests (sections 19–20 below) independently surface the same need from first principles, not from copying Jointly.
- **Devices integration**: underlying need is connected health-device data flowing into the shared record without manual re-entry. No evidence this is commonly used or essential; classified E/uncertain given Lilica's explicit exclusion of clinical/monitoring features (`docs/PROJECT_BRIEF.md`) — not recommended for investigation this phase.

## 5. Lilica advantages (protect these — do not regress in Phase 20)

Home projection, unified To Do (one canonical completion transition shared everywhere), a cleaner Calendar (a projection, not a second database), universal Add, document relationships/follow-up (link + "does anything need doing?"), a modern People/Care Circle experience, a real per-domain assignment/permission model (server-enforced, not client-hidden), a coherent information hierarchy (Home/Calendar/To Do/People/Add, not a Jointly-style module drawer), real multi-person switching, a deliberately light onboarding burden, and — per the product owner's own direct comparison — meaningfully higher visual quality than Jointly's dated, menu-driven, cumbersome presentation. None of Phase 20's candidates below should be implemented in a way that erodes any of these.

## 6. Genuine gaps (summary; full detail in section 7)

Recent Activity/care history (7A), Search (7B), Medication structure (7C, bounded/non-clinical), Contingency/emergency information (7D), Calendar device sync/export (7E), contextual record comments (a narrow slice of 7F/7G), Contact importing (7H), Notification sophistication — specifically collaboration notifications distinct from personal reminders (7J), Supported-person optional profile fields (7K, post-onboarding only), Member management/filtering refinements (7L), Export narrative/human-readability (7N).

## 7. Deliberate omissions (E — should NOT be copied)

- **General group messaging/chat.** Duplicates WhatsApp/iMessage/SMS, which families already use and are almost certainly better at real-time chat than Lilica could become without enormous investment. Building it risks turning Lilica into exactly the "large menu of disconnected modules" the brief explicitly warns against.
- **A generic, undifferentiated Notes feature.** `careNote` plus per-record `notes` fields already serve the general unstructured-information need; adding a second, parallel Notes concept purely to match a Jointly menu item would fragment "where does this information live" without adding real capability.
- **Connected health-device integration ("Devices").** Firmly inside the clinical/monitoring territory `docs/PROJECT_BRIEF.md` explicitly excludes without approval; no evidence surfaced this phase that it is commonly used or carer-critical enough to justify investigating further.
- **Copying Jointly's visual/navigational structure itself.** The product owner's own assessment (badly designed, visually dated, awkward, heavily menu/module-driven, cumbersome) is corroborated by this audit's own review of Jointly's feature list reading as a flat menu (Messages/Calendar/Notes/Tasks/Reminders/Contacts/Medications/Devices) rather than a unified model — exactly the anti-pattern section 17 of the brief warns against reproducing.

## 8. Uncertain / research-required areas (F)

- Whether Jointly's calendar recurrence handles DST transitions in a way Lilica's own recurrence engine does not already handle equally well — a small, targeted technical self-check, not a product research question.
- The exact structure/content of Jointly's "Contingency Plan" export (only its existence, not its fields, was confirmed from available sources).
- Whether Jointly has a dedicated keyword search feature distinct from its confirmed member/type filtering — not confirmed either way from available sources.
- Whether any "contextual record comment" feature (7G) could inadvertently become a backdoor into general messaging if scoped loosely — needs product-owner judgement on exact scope before any implementation brief, not further research.
- Legal/privacy research required before touching medication administration-tracking, structured health/condition fields, or emergency information — see section 11.

## 9. Recent Activity assessment (7A)

Once several people help Beauty, David cannot today answer "what has happened since I last looked?" without opening every record individually and comparing dates. Existing infrastructure: every record already has `created_at`/`updated_at`, and completion/confirmation already produces a timestamped `confirmationHistory` entry — the raw data to build a chronological feed already exists per-record, but there is no cross-record aggregation, no attribution-by-member surfaced in a feed (assignee attribution exists per-record, but "who changed this" as a general concept does not — records don't currently track a last-modified-by membership id), and no UI anywhere presents it. Building this would need: (a) a small, additive `last_modified_by_membership_id` (or similar) on the existing record row — a schema addition, not a new record type; (b) a query/RPC assembling a bounded recent-activity list, domain-filtered exactly like every other read; (c) UI, most naturally living under People/Care Circle (a "Recent activity" section on the existing Care Circle summary, or its own small screen reached from there) rather than Home, to avoid diluting Home's own calm "what needs attention" focus; (d) a small, unobtrusive Home indicator (e.g. a "New since you last looked" chip) is plausible but should be judged for restraint, not assumed necessary. Privacy/permission implications: an activity feed must respect the exact same domain-grant filtering every other read already uses — a Contributor with only `general` access must never see a financial-domain activity entry. This is assessed as the single most carer-relevant genuine gap in this audit (see prioritisation).

## 10. Search assessment (7B)

Confirmed via direct code inspection: no search feature of any kind exists. The product becomes progressively harder to navigate as a care space accumulates a year's worth of records — Home only shows Needs attention/Today/Coming up/Latest, To Do only shows open items, and People's sections have no per-section search or filter; finding "that insurance document from March" today requires manually scrolling the Documents section of People. Global search is not necessarily required at launch (the brief's own instruction: do not presume every category needs a feature), but the severity of this gap grows materially over the one-year-user horizon (section 23) — a scoped, per-tab or per-section text filter (e.g. filtering Documents/Bills/Contacts by typed text) is a materially smaller, lower-risk step than a single global search index and may be sufficient; a full global search is a larger, separate engineering decision that should not be bundled into launch-blocking scope without further evidence of real need.

## 11. Medication assessment (7C)

Lilica's current `careNote` free-text folding of medication information is not enough for a carer who needs to track a schedule, know whether a dose was actually given, or avoid two carers duplicating a dose. However, the brief is explicit: do not recommend a clinical medication-management system without analysing safety/liability implications, and this audit does not have the standing to make that legal/safety call. The bounded, carer-value slice that avoids clinical/liability territory is: structured (not free-text) fields for "what/dose/schedule" as an *information reference*, explicitly not an administration/compliance-tracking system (no "confirm dose given" workflow, no adherence analytics, no alerting framed as a medical safety feature) — closer to "a clearer place to write down what medication looks like and when it's normally taken" than "an eMAR". Even this bounded version should be routed through legal/privacy classification (F) before a product decision, per section 11 below, given the special-category-data sensitivity of any health/medication information.

## 12. Contingency/emergency assessment (7D)

Lilica has no obvious, single place answering "if something happens to me, what does another person need to know about Beauty?" today — that information is scattered across contacts, careNote records, home matters, and documents, exactly the scenario the family-handover test (section 19) and emergency test (section 20) below independently surface as a real gap. This is materially important to carers per the brief's own framing, and importantly does not require inventing new clinical concepts — it could be served by a curated, existing-data *view* (a filtered summary pulling from records/contacts/documents already entered) rather than a new record type collecting new information, which would keep the data-model impact low. Privacy/security: this view would need to respect domain-grant access exactly like everything else, and — if ever intended to be visible to someone *outside* the Care Circle in a genuine emergency — raises a materially harder question (breaking normal access control for an emergency) that is explicitly out of this audit's scope to resolve and would need its own dedicated product/legal decision.

## 13. Calendar integration assessment (7E)

No Apple/Google/device-calendar sync, import, or export exists. Two-way sync risks real duplication/confusion (an appointment edited in Lilica needs to also update the external calendar, and vice versa, which is a nontrivial reconciliation problem Lilica's own record-sync model was not designed for). A one-way, read-only export or subscription feed (e.g. an `.ics` feed URL a carer could add to their phone's calendar app) is a materially smaller, lower-risk step that avoids the two-way sync/duplication problem entirely and would very likely satisfy the underlying need ("see my caring appointments alongside my own life") without inventing new sync infrastructure.

## 14. Notes assessment (7F)

Confirmed: records already carry free-text `notes` fields, `careNote` exists as its own record type, appointment/task outcomes can be recorded via existing fields, and documents can carry their own metadata. A generic, parallel "Notes" feature purely to match Jointly's menu item is not justified — the real, narrower gap is the "contextual comment on an existing record" need identified in section 3/15G, which is a different, smaller thing than a general Notes module.

## 15. Messaging assessment (7G)

General group chat is a deliberate omission (section 7 above) — families already have better tools for that, and building it risks the exact module-drawer anti-pattern the brief warns against. The narrower need — a short, attributable, timestamped comment tied to a specific record or task ("Spoke to GP — prescription will be ready Friday") — is genuinely different from general messaging and genuinely not covered by a record's static `notes` field (which has no append-only history or per-entry attribution). This is assessed as a small, well-bounded candidate rather than a messaging feature: an append-only list of short timestamped/attributed text entries scoped to one record, reusing the record's own existing domain-access rules for who can read/write them — explicitly NOT a general inbox, NOT a notification-generating chat, and NOT a place for open-ended conversation. The risk to watch (flagged for the product owner, not resolved here) is scope creep from "comment on a record" into "general chat with an entry point that happens to be a record" — the exact boundary needs explicit product-owner judgement before any implementation brief.

## 16. Contact-import assessment (7H)

Genuine convenience win for Key Contacts (avoiding retyping a GP's or pharmacist's details already in the phone). Costs: a new `expo-contacts` dependency (not currently installed — confirmed via `package.json`), a new device permission prompt (contacts access, requested only at the point of explicit value per the app's existing permission-request pattern for camera/photos/notifications), cross-platform behaviour differences (iOS/Android contact-picker UX differs), and the ongoing question of whether an imported contact should sync back if the phone's own copy changes (recommend: no — a one-time import/copy, matching how document attachments already work, not a live sync). Low-medium engineering complexity, low regression risk (additive to the existing manual-entry Key Contacts flow, does not replace it).

## 17. Recurrence/checklist assessment (7I)

Lilica's existing Phase 8 occurrence/recurrence engine already handles interval/unit-based recurrence (week/month/year) for task/bill/homeMatter records and produces one deterministic next occurrence on completion, with immutable prior-version history. This already adequately serves weekly shopping, bins, recurring bills, and routine check-ins as recurring tasks. No gap was found here — the existing engine should not be duplicated or replaced.

## 18. Notification assessment (7J)

Phase 14's reminder engine covers personal, date-driven reminders well (a "Remind me" toggle with conservative offsets and quiet hours) but is architecturally scoped to the *individual's own* dated records — there is no notification of any kind when another Care Circle member assigns something to you, completes something you were tracking, changes an appointment date, uploads a document, or accepts/sends an invitation. The brief's own framing is correct to separate these: a REMINDER ("this thing you set is due soon") is a fundamentally different concept from a COLLABORATION NOTIFICATION ("someone else in your circle did something"), and Lilica has only built the first. Given Phase 14's own architecture (local-only, no server/push infrastructure), collaboration notifications would need genuinely new infrastructure (most plausibly, they'd depend on section 9's Recent Activity feed existing first, since a collaboration notification is naturally "tell me about a new activity-feed entry that concerns me" rather than a wholly separate concept) — this is flagged as dependent on 7A, not independent of it.

## 19. Supported-person information assessment (7K)

Jointly collects DOB, condition, caring needs, likes/dislikes on a profile page. Lilica deliberately excludes DOB and has no equivalent structured fields today. Some of this information is genuinely useful (a new or occasional helper benefits enormously from "likes tea not coffee, gets anxious about noise, allergic to penicillin" being in one obvious place) — but the brief's own reasoning is correct that usefulness does not imply it belongs in onboarding: Lilica's onboarding is deliberately light, and forcing a "giant dossier" at setup time would directly regress that advantage. Any such fields, if pursued, should be optional, added post-onboarding (e.g. from People's own supported-person header, "add profile details" as a discoverable but skippable action), and DOB specifically should remain excluded absent a demonstrated need overriding the existing deliberate decision. Structured health/condition/allergy information additionally carries a real special-category-data classification under UK GDPR (see section 11) — a genuine gap in convenience, but one requiring the F (legal/privacy research) track before any C-level implementation commitment, not a straightforward product decision.

## 20. Care Circle/member-management assessment (7L)

Lilica's current Care Circle already exceeds Jointly on the security/permission dimension (explicit per-domain grants, server-enforced, immediate-effect removal) — a genuine advantage, not a gap. The gaps found are narrower: no client-facing list of former members (data exists per Phase 18B, no screen surfaces it — small, low-risk addition if a genuine need is confirmed, e.g. for historical-attribution transparency); no filtering of records/tasks by "show only what member X is involved in" (Jointly's confirmed "filtering across Events, Notes, Reminders, Tasks"); no in-app role-change UI (the `change_member_role()` RPC exists and is tested, documented as deliberately deferred since Phase 15). None of these are large — each is closer to a UI-only addition on existing, already-secure server capability than a new capability.

## 21. Offline assessment (7M)

Lilica's offline architecture (Phase 7's account-scoped cache/outbox, Phase 16/18's retry queues for attachments/cleanup) is substantial and was not re-audited at the mechanism level this phase (Phase 19 already validated it; re-litigating sync internals is explicitly out of Phase 20's scope, and the brief says not to rebuild the sync system). Whether this represents parity, advantage, or a gap relative to Jointly's own current offline depth is genuinely UNCERTAIN from available public sources — Jointly's marketing emphasises "practical carer access" without technical detail on its own offline guarantees. No action recommended; not identified as a gap requiring investigation.

## 22. Export/handover assessment (7N)

`export_my_data()` is technically complete (every authorised record, link, and real downloaded document file, domain-filtered) but produces a JSON document plus a pile of individual files — genuinely complete data, but not something a human carer would find useful in an emergency or handover ("here's 40 files and a JSON blob" vs. "here's a one-page summary of what matters right now"). A distinct, human-readable summary view (care summary / emergency summary / handover summary) built from already-existing data would materially improve the *usefulness*, not the completeness, of what Lilica already exports — and would likely share underlying data-selection logic with the Contingency/emergency assessment (section 12) and the Recent Activity feed (section 9), making these three candidates naturally sequenced rather than independent.

## 23. One-year-user findings

Modelling a 12-month user with two supported people, hundreds of records, many completed tasks/appointments, dozens of documents, several Care Circle members, historical bills, and recurring responsibilities: **search** becomes the most acute difficulty (finding one document or bill among dozens with no search/filter at all); **history/activity** becomes acute in any multi-member circle (no way to see what happened while away); **document retrieval** specifically suffers without search or grouping (Phase 17's own named, deliberate scope reduction — no "Expiring soon"/"Recently added" grouping — compounds this over time); **member activity** (who's been doing what) becomes opaque exactly as a circle grows, which is when it matters most; **old records** themselves remain individually retrievable via existing sections (nothing is deleted or hidden), so the problem is discovery, not data loss.

## 24. Family-handover findings

Modelling David becoming unavailable and Marion needing to take over Beauty's care tomorrow: Marion (once granted appropriate Care Circle access) CAN determine what's happening soon (Calendar/Home), what needs doing (To Do), what medication/health information matters only as well as whatever free-text `careNote` entries happen to exist (no structured summary), where important documents are (People's Documents section, if she knows to look there), and what bills/renewals are approaching (To Do/Home). She CANNOT easily determine what has already been done recently (no activity feed — she'd have to infer from individual record timestamps) or what recent changes happened while she wasn't looking. This is a meaningful, real failure directly corroborating the Recent Activity gap (7A/9) and motivating the Contingency/handover-summary candidate (7D/7N) as genuinely carer-relevant rather than speculative.

## 25. Emergency-test findings

Modelling a family member needing critical information about Beauty unexpectedly: today Lilica can provide whatever is already recorded in Key Contacts, careNote entries, and documents — but only if the person knows Lilica well enough to navigate to the right section and has appropriate Care Circle access already granted (invitations are not instant; a brand-new emergency helper without prior access has no path to see anything). Lilica cannot today provide a single, fast "here's what matters" view. This audit does not recommend Lilica attempt to become an emergency medical record (explicitly out of scope per the brief and `docs/PROJECT_BRIEF.md`'s own exclusions) — the reasonable, bounded value-add is a curated summary view built from existing data for someone who ALREADY has appropriate access, not a new access-control bypass or a new category of clinical data collection.

## 26. Six-person collaboration findings

Modelling a Care Circle of six people: current Lilica already lets everyone see (within their granted domains) who is assigned what and whether it's complete (To Do's own filters, Phase 15's domain-grant model), and the organiser can see the member list and their granted domains (Care Circle screen). The genuine gaps are exactly the ones already identified above, now more acute at this scale: nobody can easily tell *what changed* recently without opening every record (7A); avoiding duplicated effort depends entirely on people already knowing to check To Do/Calendar diligently, since there's no "someone else just started this" indication; permissions remain understandable (Phase 15's explicit per-domain model is a genuine strength here, not a gap); a member can leave safely (Phase 15's `leave_care_space()`/removal, immediately effective); historical contribution remains only partially understandable (a former member's past work is correctly retained and attributed per Phase 18B, but is not surfaced anywhere as a coherent "what did they contribute" view).

## 28. Legal/privacy flags

Classified for specialist review, not concluded here: structured medication/health-condition information (7C, 7K) is special-category data under UK GDPR and would need a genuine legal/privacy review before any schema commitment, not just a product decision; any contingency/emergency information intended to be visible outside the normal Care Circle access boundary (7D) raises an access-control exception that needs explicit legal/product sign-off, not an engineering default; contact importing (7H) touches third-party personal data (the imported contact did not consent to being in Lilica) and should be reviewed for what UK data-protection guidance says about importing third-party contact data via a consumer app; any future collaboration-notification/messaging-adjacent feature (7G, 7J) should be reviewed for message-retention expectations before real content persistence is added. No legal conclusions are drawn in this document, per the brief's own instruction.

## 29. Prioritisation (P0–P3)

Conservative on P0, per the brief's own instruction — a competitor having a feature does not make it P0.

- **P1 (strong pre-launch improvement)**: Recent Activity/care-history feed (7A) — the single most carer-relevant gap found, directly corroborated by three independent tests (one-year-user, family-handover, six-person collaboration) rather than only the competitor comparison; a scoped per-section search/filter (7B, the small version, not full global search); Contingency/emergency summary view (7D) — bounded, reuses existing data, no new data collection.
- **P2 (useful post-launch improvement)**: Medication structure, bounded and non-clinical, pending legal/privacy classification (7C); Calendar `.ics` export feed (7E); contextual record comments (7G), pending explicit scope-boundary decision from the product owner; contact import (7H); collaboration notifications (7J) — sequenced after 7A since it depends on it; supported-person optional profile fields (7K), pending legal/privacy classification for health-adjacent fields; former-member visibility / member filtering refinements (7L); export narrative summary (7N) — sequenced after 7A/7D since it likely shares data-selection logic with both.
- **P3 (optional / evidence needed)**: Full global search index (vs. the smaller P1 scoped-filter version); Google Calendar/Apple Calendar two-way sync (as opposed to the P2 one-way export); DST-recurrence technical self-check (7 in section 8).
- **P0**: none identified. No candidate in this audit rises to "launch-critical deficiency" — every genuine gap found has either a workable narrower interim (search-as-filter vs. full index; export vs. two-way sync) or a legal/privacy gate that must clear before any commitment.

Both fit naturally into the existing People/Care Circle and per-tab models respectively, require no new record type, and directly address the gap most independently corroborated by this audit's own family-handover/one-year/collaboration tests.

MINIMUM, plus: a Contingency/emergency summary view (7D, M effort, reusing 7A's data-selection groundwork) and contact import for Key Contacts (7H, S/M effort, additive and low-risk).
