# Phase 7 Record Persistence Architecture

Status: Implemented, physically verified and approved in the client and `lilica-development`
Date: 10 September 2026

## Boundary

Phase 7 makes Supabase the durable source of truth for records while retaining an account-scoped, care-space-partitioned AsyncStorage cache for startup and offline use. Local mutations enter a durable semantic outbox before synchronisation. The existing record-entry and Home presentation remain unchanged.

Phase 7 does not implement occurrences, assignments, invitations, additional member roles, permission-management UI, cloud attachment bytes, realtime subscriptions, Calendar, To Do, notifications, OCR, or Ask Lilica.

## Server Records

`public.records` stores:

- client-stable UUID and required `care_space_id`;
- preserved local record ID and current Lilica record type;
- current record data required to reconstruct `LilicaRecord`;
- generated domain and sensitivity classification;
- active/archive lifecycle and a deletion tombstone;
- descriptive responsibility text and its provenance;
- attachment metadata only;
- server-derived creator/updater membership, source, timestamps, version and change sequence.

Clients receive `SELECT` only. Creates, imports, updates and deletes use `apply_record_mutation(...)`, which validates active organiser membership, operation identity, care-space ownership and base version. `public.record_mutation_receipts` makes retry after a lost acknowledgement idempotent. Remove writes a tombstone; there is no client hard-delete path.

## Classification And Access

Classification is generated by the database from the current user-facing type:

| Types | Domain | Sensitivity |
|---|---|---|
| appointment, task, contact, update | general | standard |
| careNote | health | sensitive |
| bill | financial | sensitive |
| homeMatter | home | standard |
| document | documents | sensitive |

This is a conservative Phase 7 substrate, not a medical inference. `can_access_care_space_records(...)` centralises the policy boundary. Today it permits only an active organiser membership. Phase 15 may extend this helper with capabilities/domain grants without changing record ownership. Assignment never grants visibility.

`care_space_memberships.membership_status` currently supports `active` and operator-set `revoked` solely so RLS can deny stale clients immediately. Invitation/member-management lifecycle remains Phase 15.

## Local Cache And Outbox

The operational cache key is:

```text
lilica:record-cache:v1:{auth-user-id}
```

Each care-space entry independently stores cached records, local-to-cloud identity mappings, server versions/base snapshots, outbox operations, preserved conflicts, pull cursor and migration checkpoint. The prior `lilica:onboarding:v1:{auth-user-id}` state remains a backward-compatible snapshot and migration source; it is not deleted after upload.

Outbox operations are `create`, `import`, `update`, and `delete`. Each carries a stable operation UUID, care-space ID, local/cloud record IDs, payload/base snapshot, attempt count, status, error and retry time. Retries use capped exponential delay with deterministic jitter and run only while authenticated through startup, foreground, local work, or a pending retry timer.

## Identity And Migration

New records are created with UUIDs. A valid historical UUID remains the cloud record ID. Any older non-UUID ID maps deterministically from account ID, care-space ID and local record ID; that mapping is persisted and regenerated identically after interruption.

The first cache preparation inventories each linked care space once and creates stable `import` operations. Migration progresses from pending to uploading and becomes complete only after server acknowledgement and a successful authorised pull. Interrupted or response-lost imports retain their outbox entry and retry without duplicate rows.

`responsiblePerson` is stored as `legacy_responsibility_text`, with `legacy_local_record` or `native_free_text` provenance. It is never matched to a profile, email or membership and never grants access. Phase 8 owns assignment identity.

## Reconciliation

The client pushes ordered per-record operations, then pulls rows/tombstones newer than its durable change cursor. Direct same-version edits apply atomically. A stale update includes its last confirmed base snapshot:

- fields changed on only one side merge;
- the server preserves unrelated remote fields;
- competing changes to the same field return a conflict;
- stale delete conflicts rather than deleting newer work.

Conflicting/rejected operations remain durable and are not retried forever. Phase 7 intentionally has no new conflict-resolution UI; review/recovery UI requires separate product approval. Realtime is not used.

Mutations remain ordered per cloud record: an unresolved retry, rejection or conflict blocks later operations for that record from overtaking it. A blocked remote row holds back the durable cursor, while unrelated later rows may still be applied idempotently and will be seen again on the next pull until the cursor can advance safely.

## Attachments

Local attachment files and full local references remain in the device cache. Only metadata excluding device-local URI is included in the cloud record. The originating device continues to use its local URI. Another device can reconstruct the record but does not claim that unavailable bytes are present. Cloud upload, download, sharing, versioning and OCR remain deferred.

## Operations

```bash
npm run validate:all
npx supabase db push --linked --dry-run
npx supabase db push --linked
```

Only linked `lilica-development` may be changed. Never reset the linked project or create/touch production. See `docs/SUPABASE_OPERATIONS.md`.

## Known Limitations

- Conflict and rejected-mutation state is retained internally but has no user-facing recovery screen.
- Remote changes are pulled at startup/foreground and during local sync; realtime invalidation is deferred.
- Attachment bytes are not available on a second device.
- Privacy/interests/setup progress remain device-local; a newly discovered cloud care space resumes those local gates rather than inferring consent.
- Only the Phase 6 organiser role participates; collaboration and granular grants remain Phase 15.
