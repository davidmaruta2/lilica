# Phase 15 Care-Circle Invitations And Collaboration Architecture

Status: database layer (invitations, roles, domain grants, assignment-visibility enforcement) implemented and automatically validated (pgTAP + Jest); client layer (Care Circle screen, invitee-facing Invitations screen, real assignment selector) implemented and automatically validated; physical two-real-account device QA pending (see `docs/PHASE_15_QA.md`)
Date: 11 September 2026 (Invitations screen added same day, as a follow-up slice)

## Boundary

Phase 15 makes sharing a Lilica care space **real, explicit, permissioned and revocable** between genuine Supabase accounts. It extends - rather than duplicates - the Phase 6/7 membership/RLS skeleton: `care_space_memberships.membership_status` (active/revoked) already existed and is reused unchanged for removal/leaving; `can_access_care_space_records()` was already the designated Phase 15 extension point (code-commented as such since Phase 7); the domain taxonomy (general/health/financial/home/documents) already existed via `record_domain_for_type()`.

Out of scope, deliberately not touched: Home/Calendar/To Do/Person/onboarding/auth redesign, Phase 7 sync internals, Phase 14's reminder engine internals (only reused as-is), document cloud maturity, OCR, Ask Lilica, search/history, professional/agency workflows, emergency access, Phase 16+.

## Core Invariant

Sharing must be real, explicit, permissioned and revocable. Nothing in this phase infers membership, role, or visibility from a name, email, relationship label, contact, or the legacy `responsiblePerson` free-text field. A pending invitee is never a member, is never assignable, and is authorised to read nothing.

## Locked Invariant: Assignment ≠ Permission

"Who is expected to deal with this" (assignment) and "who is allowed to see this" (permission/visibility) are kept strictly separate, and assignment must never grant permission:

- `apply_record_mutation()` (redefined, same signature, in `supabase/migrations/20260911120000_phase15_care_circle.sql`) now validates any `assignedMembershipId` present in the merged record data: the target membership must (a) be **active** in this care space and (b) have **read access to this record's actual domain**. Either failure raises `42501` and the whole mutation is rejected - never silently dropping just the assignment.
- This closes two real gaps that existed before Phase 15: the write-access check was hardcoded to the `'general'` domain regardless of the record's real domain (would have wrongly gated/ungated contributors with partial grants), and `assignedMembershipId` was never validated at all - any value round-tripped through `record_data` unchecked.
- Because the check re-runs on every mutation (not only the one that first sets the assignment), a **replayed/offline mutation cannot recreate access for a since-removed member** by re-sending the same assignment - Scenario H's fixed test in `supabase/tests/database/phase15_care_circle.test.sql`.
- Removing a member never rewrites a record's historical `assignedMembershipId` - attribution is retained. The client is responsible for rendering "assignee no longer has access" when the assigned membership is not in the current active member list (not yet built as its own UI affordance; `careCircleMembers` from `src/careCircle.ts` is the source of truth a screen would check against).

## Role Presets And The Capability/Grant Model

Three role presets, not "dozens of roles": **Organiser**, **Contributor**, **Viewer** (`care_space_memberships.role`, CHECK-extended from the Phase 6 organiser-only constraint). Role is a convenience preset, not the sole security boundary - it sits over an explicit per-domain grant model:

- `care_space_domain_grants` - one row per `(membership_id, domain)` a **non-organiser** has been explicitly given `can_read`/`can_write` on. Organisers need no rows here; their role alone grants full, unconditional access to every domain, unchanged from Phase 7/8/9.
- `membership_has_domain_access(membership_id, domain, action)` - the shared access decision, keyed by membership ID rather than caller identity, so it can answer both "can the caller do X" (via `can_access_care_space_records()`, unchanged signature, now delegating to this) and "does this OTHER membership have visibility" (the assignment check above).
- **Default-deny**: a domain not explicitly granted is invisible to a contributor/viewer, full stop - there is no implicit "general access for everyone" fallback. An invitation's `granted_domains` is chosen explicitly by the inviting organiser (the Care Circle screen's invite form asks them to review it before sending, per the brief's "review access before send" requirement) and is exactly what the resulting membership's grant rows become on acceptance.
- A viewer's grant rows are always `can_write = false`; a contributor's are `can_write = true` for whatever domains they were granted. Changing a member's role (`change_member_role()`) replaces their grant rows wholesale with the new set passed in - never merges stale ones forward.

## Invitation Lifecycle

`care_space_invitations`: `pending → accepted | declined | expired | revoked` (all terminal except pending). Fields: `care_space_id`, `invited_by_membership_id`, `invitee_email` (normalised lower-case), `role` (`contributor`/`viewer` only - an invitation can never directly grant `organiser`), `relationship_type`/`relationship_label` (reuses the exact same CHECK-constrained vocabulary as `care_space_memberships`, including the "label required for Other relative/Someone else" rule), `granted_domains`, `operation_id` (idempotency), `created_at`/`expires_at` (14-day default), `responded_at`, `accepted_membership_id`.

- **`invite_member()`** - organiser-only (checked against the caller's own active organiser membership in that space, not client-asserted). Rejects inviting someone who already has active access. Upserts (via a partial unique index on `(care_space_id, lower(invitee_email)) where status = 'pending'`) rather than duplicating a still-pending invite to the same address - a re-invite refreshes role/domains/expiry.
- **`list_my_invitations()`** - the invitee's own pending, unexpired invitations only, resolved by their authenticated email (`auth.jwt() ->> 'email'`), never by any client-supplied identity. Lazily flips anything past `expires_at` to `expired` on read, so an expired invitation is never silently still acceptable. This is a SECURITY DEFINER function, not a direct table SELECT - an invitee has no membership yet to scope table-level RLS against, so `care_space_invitations`' own RLS policy only lets an **organiser** SELECT directly; the invitee's access is exclusively through this function.
- **`accept_invitation()`** - verifies the caller's own authenticated email matches the invitation, verifies it is still pending and unexpired, then creates (or **reactivates**, if this user held a since-removed membership in that same space - `care_space_memberships` allows only one row per `(user_id, care_space_id)`) the real membership with exactly the invitation's role/relationship/domain grants, and marks the invitation accepted with `accepted_membership_id` set.
- **`decline_invitation()`** - invitee-only, pending-only.
- **`revoke_invitation()`** - organiser-only, pending-only. A revoked invitation is a hard terminal state (cannot be revoked again, cannot later be accepted).

## Membership Lifecycle: Removal And Leaving

Both **reuse the existing `membership_status` active/revoked column** - no new column, no parallel lifecycle. Every RLS check and `can_access_care_space_records()` call already keys on `membership_status = 'active'`, so a revoked membership loses access immediately and everywhere the moment the row is updated - DB, RLS-gated reads, and any client re-sync alike.

- **`remove_member()`** - organiser-only. Refuses to remove the sole remaining active organiser (a care space can never be left without one).
- **`leave_care_space()`** - a member revoking their own membership. Same sole-organiser protection: a sole organiser must hand organiser role to someone else first (`change_member_role()`), or leaving is refused with an explanatory error.
- **`change_member_role()`** - organiser-only. Refuses to demote the sole remaining organiser. Replaces the target membership's domain grants wholesale with the new set passed in.
- Role itself became a legitimately-changeable field in this phase: Phase 6's `protect_membership_identity()` trigger originally treated `role` as an immutable ownership identifier (safe at the time, since `'organiser'` was the only allowed value). It is redefined here to keep `care_space_id`/`user_id`/`bootstrap_id` immutable but allow `role` to change - authorised exclusively by `change_member_role()`'s own organiser + sole-organiser-safety checks, never by direct client `UPDATE`.

## Member Display

`list_care_space_members(care_space_id)` returns active members only (never pending/declined/expired/revoked/removed/left), each with `membership_id` (the real, stable identity), a human-friendly `display_name` (from `profiles`), `role`, `relationship_type`/`relationship_label`, `is_self`, and `granted_domains`. Display name is sourced live from `profiles` on every call - changing it never touches any stored assignment, because assignment is keyed by `membership_id`, never by name. This is the same "no name matching, ever" discipline the legacy `responsiblePerson` free-text field has always been held to.

## Real Assignment Selector (extends Phase 9)

`src/components/RecordEditor.tsx`'s "Assigned to" control previously offered only Unassigned/You (`activeMembershipId`). It now accepts an optional `careCircleMembers: CareCircleMember[]` prop (from `App.tsx`'s `listCareSpaceMembers()`, refreshed whenever the active care space changes or Care Circle is opened) and, when present, offers every member with visibility into **this record's domain** - computed client-side via the new `recordDomainForType()` in `src/records.ts` (an exact mirror of the server's `record_domain_for_type()`), filtering `careCircleMembers` to `role === 'organiser' || grantedDomains.includes(domain)`. This is a courtesy (a clearer, non-broken picker) - the server-side check in `apply_record_mutation()` is what actually enforces the invariant; the client filter can never be the only thing standing between a forbidden assignment and the database. With no `careCircleMembers` prop supplied (a local-only care space, or before the first fetch resolves), the control falls back to exactly its pre-Phase-15 Unassigned/You behaviour - existing Phase 9/12/14 tests pass unchanged.

## Client Boundary (`src/careCircle.ts`)

A thin, typed RPC wrapper module, following the same pattern as `src/careSpaces.ts`: every function maps snake_case RPC rows to camelCase types and never throws (`{ ok, data | message }`). No authorisation logic lives here - every function's actual authority comes from the server function it calls. `inviteMember`, `listMyInvitations`, `acceptInvitation`, `declineInvitation`, `revokeInvitation`, `listCareSpaceMembers`, `listCareSpaceInvitations`, `changeMemberRole`, `removeMember`, `leaveCareSpace`.

## Invitations Screen (`src/screens/InvitationsScreen.tsx`)

The invitee-facing entry point: lists this signed-in account's own pending invitations (`listMyInvitations()`, scoped server-side to the caller's authenticated email - never a client-supplied identity) with Accept/Decline per invitation, each showing which care space, who invited them, their role, and exactly which domains they'd be able to see.

- **Auto-surfaced once per app session.** `App.tsx` fetches `listMyInvitations()` in the same effect that already runs `reconnectCareSpaces()` once per signed-in owner (right after `auth.profile` resolves). The first time that fetch returns any pending invitation, the screen opens automatically - ahead of the normal onboarding/Home flow, so a brand-new invitee who just signed up specifically to accept sees it immediately rather than being routed into "set up your own care" first. It does not reopen itself again this session after being dismissed.
- **"Not now" leaves everything untouched** - the invitation stays pending, fully unaffected, and the user returns to normal use. To come back to it later without waiting for a fresh app launch, Person's header shows an "Invitations (N)" link whenever `myInvitations.length > 0`, next to Care Circle/Account.
- **Accept** calls `acceptInvitation()`, then - on success - the *existing*, unmodified `reconnectCareSpaces()`/`integrateReconnectedCareSpaces()` flow (the same one every signed-in device has always used to rediscover its own care spaces) picks up the newly created membership with no Phase-15-specific client plumbing needed, because `list_my_supported_people()` was never role-filtered. The invitations list is then refetched from the server (never assumed locally) so a failure leaves the invitation exactly as it was, and a success reflects the server's own resulting state, not an optimistic guess.
- **Decline** calls `declineInvitation()` and refetches the same way.
- A failed accept/decline shows the server's own error message inline against that specific invitation and leaves it in the list - never silently removed, never implied successful.
- Once the list empties (every invitation resolved), the screen closes itself automatically.

## Care Circle Screen (`src/screens/CareCircleScreen.tsx`)

Reachable from Person's header via a "Care Circle" link (next to the existing "Account" link), shown only when the active care space is a real (non-`local-`) synced space with a membership - matching Person's own precedent for `onOpenAccount`. Shows the active member list (with role, relationship, and - for non-organisers - exactly which domains they can see), pending invitations with a cancel action, and an invite form: email, relationship label, role (Contributor/Viewer), and an explicit domain checklist the organiser reviews before sending (default-deny - nothing is pre-selected beyond "Everyday things"). Removing a member or cancelling an invitation re-fetches both lists from the server afterwards, so the screen never shows an optimistic guess about server-authoritative state.

## What Is Deliberately Not Built Yet

Documented here rather than silently absent, matching this project's established honesty precedent (see Phase 14's own "deferred" section):

- **No push/email delivery of the invitation itself.** An invited person currently discovers their invitation only by opening Lilica and having `list_my_invitations()` return it - there is no email sent, no push notification. Reusing Phase 14's local-notification engine for "you have an invitation" / "your invitation was accepted" / "work was assigned to you" (brief sections 39-40) is designed for (the domain/permission model is already in place to support it safely) but not yet wired up.
- **No dedicated "assignee no longer has access" UI treatment.** The data needed for a screen to detect and show this (comparing a record's `assignedMembershipId` against the current active `careCircleMembers` list) is available via `src/careCircle.ts`, but no screen renders that state specially yet - an editor currently just shows the assignment control's normal Unassigned/named-member options, with the previously-assigned-but-now-inactive member simply absent from the offered list.
- **No progressive-disclosure "change role" UI.** `change_member_role()` exists and is pgTAP-tested; the Care Circle screen does not yet expose a control to call it (only invite and remove are wired into the UI).
- **No organiser self-service "make someone else organiser then leave" flow in the UI**, though the underlying `change_member_role()` + `leave_care_space()` functions and their sole-organiser-safety checks are implemented and tested.

None of this is faked - the app never claims an invitation was sent by email, never shows a stale assignee as if they still had access, and never offers a role-change control that doesn't work. It is simply not yet built, exactly as stated here.

## Addendum (12 September 2026): Server-Side Permission Verification

A pre-Phase-16 investigation (`docs/PHASE_16_DOCUMENTS_INVESTIGATION.md`) flagged a suspected gap after reading only `supabase/migrations/20260910150000_phase7_records.sql` in isolation: that file's own `can_access_care_space_records()` hard-codes `role = 'organiser'`, which read alone would mean a Contributor/Viewer's domain grants are never actually honoured server-side.

A dedicated follow-up verification (investigation only, no code changed) established this is **not a real gap in the deployed database**. `supabase/migrations/20260911120000_phase15_care_circle.sql:168` redefines the same function (`create or replace function public.can_access_care_space_records(uuid, text, text)` - identical name and signature) to delegate to the new `membership_has_domain_access()`, which correctly implements organiser-unconditional / contributor-or-viewer-by-explicit-grant / revoked-membership-never access. Because Postgres RLS policies and other functions reference a function by name+signature rather than a frozen body, every existing caller - the `records` table's own read policy (`phase7_records.sql:219-221`), `apply_record_mutation()`'s write check, and the Phase 8 occurrence-table policies - automatically runs this Phase 15 body with no changes needed at any call site. No later migration redefines the function again.

This is confirmed deployed (not just written locally) per this file's own "Hosted Phase 15 deployment" entry in `docs/SUPABASE_OPERATIONS.md`, and directly exercised by the 31 pgTAP assertions above - in particular the contributor-granted-vs-ungranted-domain pair (lines ~53-94 of `phase15_care_circle.test.sql`), the viewer-can-read-but-not-write pair, and the immediate-zero-access-on-removal pair, all run as real authenticated Postgres sessions, not isolated unit assertions. `membership_has_domain_access()` has no domain-specific branching, so this holds for the `documents` domain exactly as it does for `general`/`financial`/`home`/`health`, even though no existing pgTAP scenario names `documents` literally - a follow-up assertion doing so (mirroring the existing `financial` scenario) would be a cheap, optional confidence-raiser before Phase 16 leans on this, but is not evidence of a known problem.

## Addendum (14 September 2026): Invitation Deep-Link Physical Test Failure -- Canonical Link Contract And Root Cause

A physical, real-iPhone test of the full invitation journey found: real email delivery to a real inbox, and opening the hosted `lilica.co.uk` landing page, both **PASS**. Tapping "Open in Lilica" on that page then produced iOS/Safari's own error, **"Safari cannot open the page because the address is invalid."** This is recorded honestly as a **FAIL** for the landing-page-to-installed-app hand-off step specifically -- it does NOT mean the wider invitation journey has been fully proven end to end, and no automated test result should be read as having proven this step.

**The canonical invitation link contract, confirmed by direct inspection of every component (not assumed):**
- Public web link (email, Share): `https://lilica.co.uk/invite/?id=<invitation-id>` -- the invitation's own `care_space_invitations.id`, as a query parameter (see this file's own routing-decision entry in `docs/REVISION_LOG.md`, 14 September 2026).
- Native custom-scheme link (built client-side by the landing page's own script, and by `src/invitationLinks.ts`'s `invitationAppUrl()`): `lilica://invite/<invitation-id>` -- a path segment. This is the ONE format both places generate; there is no second, divergent format anywhere in the codebase (audited: `public/invite/index.html`, `src/invitationLinks.ts`, `src/invitationDeepLink.ts`, `app.json`, `App.tsx`).
- `app.json`'s top-level `"scheme": "lilica"` is what Expo's build tooling uses to register this scheme with iOS (`CFBundleURLSchemes`) and Android (an intent filter) -- confirmed correctly present and correctly resolved by `npx expo config --type introspect`.

**Root cause, established by direct inspection, not guessed:** the link chain itself is syntactically and architecturally correct end to end. The landing page constructs a well-formed `lilica://invite/<uuid>` URL; `app.json` correctly declares the scheme Expo would register in a real build. The failure is environmental: **no EAS development or production build of Lilica has ever been created** (a standing, previously-documented fact -- see `CLAUDE.md`'s EAS-build-requirements entry). The test device was necessarily running Expo Go, and **Expo Go cannot and does not register a third-party app's own custom URL scheme** -- this is a fundamental Expo Go limitation, not a Lilica configuration mistake. iOS's "address is invalid" message is its standard, generic wording for ANY custom scheme with no registered handler on the device; it is not evidence the URL itself is malformed, and direct inspection confirms it is not. **No code change can fix this without a real installed build** -- see `CLAUDE.md`'s standing EAS-build-consent requirement; none is implied or requested by this addendum.

**What WAS genuinely fixed this pass** (independent of the above, and worth keeping regardless of when a build happens): the landing page's copy previously read "If you already have Lilica installed, tap below..." followed by a store-availability sentence -- together implying that a failed tap proves the app isn't installed, which this page cannot actually know (the real failure mode, above, has nothing to do with whether a hypothetical build is on the device). Split into two separate, calmer statements: "Already have Lilica? Open this invitation in the app." and, separately, "Lilica isn't publicly available in the App Store or Google Play yet." Confirmed (from the physical-test screenshot itself) that a failed tap leaves the landing page fully intact underneath iOS's own dismissable alert -- the user is never stranded on a broken page, confirmed by direct observation, not assumed.

This local-reference-copy fix (`public/invite/index.html`) has **NOT** been pushed to the live `github-pages-hosting` branch this pass -- this task's own stop condition ("DO NOT COMMIT. ## Addendum (14 September 2026): Care Circle Invitation & Joining Flow Completion

A HOLISTIC, additive extension (`\downloads\carecircle.txt`) requested by physical testing plus an agreed enhancement: an invitee must be able to join a Care Circle manually, by code, without depending entirely on an email/deep link. This did NOT touch the invitation architecture, the acceptance authority, the membership architecture, or the permission/domain model -- all four remain exactly as this file already describes them, confirmed by direct inspection before any code was written (per this brief's own explicit instruction).

**The human-friendly invitation code.** `care_space_invitations` gains one additive column, `invite_code` (`supabase/migrations/20260916140000_invitation_code.sql`): 8 characters, an unambiguous alphabet (`ABCDEFGHJKMNPQRSTUVWXYZ23456789` -- no `0`/`O`, `1`/`I`/`L`), generated server-side (`generate_invitation_code()`, retries on collision, never derived from a user id/care-space id/email), unique, backfilled for every pre-existing row. `invite_member()`'s own `on conflict ... do update` re-invite path deliberately does NOT reassign the code -- the column default only fires on INSERT, so re-inviting the same email keeps whatever code the organiser may have already shared. The code is a LOCATOR, never a second security model: it identifies which invitation someone means, nothing more.

**`resolve_invitation_by_code(code_input text)`** (SECURITY DEFINER, `authenticated` only) is the ONLY new way to reach an invitation by code. It returns a deliberately minimal preview -- `id`, `care_space_name` (the supported person's first name), `invited_by_display_name`, `role`, `granted_domains` -- and NEVER `invitee_email` or `care_space_id`. Lazily expires a stale row first (mirroring `list_my_invitations()`'s own established pattern), then distinguishes two calm failure states: "We could not find an active invitation with that code" (truly nonexistent/malformed) versus "This invitation is no longer active" (a real invitation that is revoked/accepted/declined/expired -- the brief's own explicitly-permitted "where the server can safely distinguish it" case, since confirming a code the caller already possessed was once real leaks nothing new). Deliberately permissive about WHO may preview: any authenticated caller, not just the invited identity -- previewing exposes nothing sensitive, and the real security boundary is entirely unchanged and lives where it always did.

**Identity security is unweakened, proven directly (not merely asserted).** `resolve_invitation_by_code()` never checks the caller's identity against the invitation -- acceptance still goes through the completely unmodified `accept_invitation()`, which still requires the authenticated caller's own email to match `invitee_email`. A new pgTAP test (`supabase/tests/database/invitation_code.test.sql`, 15 assertions, all passing locally and the migration applied cleanly to `lilica-development`) proves this directly: an unrelated authenticated account can resolve a code's preview but is refused ("Invitation not found") when it tries to accept the same invitation id; the genuinely invited account, resolving the SAME code, succeeds; the resulting membership's role and domain grants are exactly what the invitation specified, never broadened by having been reached via a code.

**Client**: `resolveInvitationByCode()` (`src/careCircle.ts`) -- deliberately NOT routed through the shared `fail()`/`friendlyAuthError('profile')` helper used by every other function in that file, since that helper's generic fallback ("Your profile could not be saved just now") is written for account/profile actions and would silently replace this function's own calm, specific messages with an unrelated one. A REAL, PRE-EXISTING GAP was found in the course of this: `friendlyAuthError('profile')` already swallows every OTHER Care Circle RPC's own specific error text (e.g. `invite_member()`'s "A short relationship label is required...") into that same generic fallback today, for every existing invitation function (`inviteMember`, `acceptInvitation`, `declineInvitation`, `revokeInvitation`). This is real and worth fixing, but it is unrelated to this brief's own scope (Category E, "unrelated" -- must not be implemented here) and is flagged here rather than silently patched.

**"Join a Care Circle."** One new screen, `src/screens/JoinCareCircleScreen.tsx` (code entry -> a calm review of the real inviter/person/role/domain-description preview -> explicit Join, never a silent accept), reachable from two places, both converging on the exact same component and the exact same `onAccept` callback (in the real app, App.tsx's own `handleAcceptInvitation()` -- never a second acceptance path):
- A genuinely new user's onboarding: the ONLY authorised onboarding change, a single narrow routing fork (`src/screens/JoinOrSetupScreen.tsx`, "What would you like to do? / Set up care for someone / Join a Care Circle") inserted immediately before -- never replacing -- the existing `careFork` screen, shown only when `initialPersonStage()`'s own existing `!hasStarted` condition is true (a user with no accessible care space and no in-progress draft) and only once both of that function's callers have already confirmed no auto-surfaced invitation is currently being shown. ## Addendum (14 September 2026): Final Architectural Closure -- Server-Authoritative Delivery State, Code Rate Limiting, Shared Avatar Visibility

Three further, separately-requested corrections, closing genuine gaps the prior two addenda had honestly flagged rather than silently fixed.

**1. Delivery state moved server-side.** The prior addendum's own `invitationDeliveryStatus` (`LocalCareSpaceState`/AsyncStorage) was explicitly named as per-device-only, not durable server truth. GPT/product-owner review correctly identified this as unacceptable for something Lilica itself already knows: whether it successfully submitted an invitation email to Resend. Fixed with three additive columns on the EXISTING `care_space_invitations` row (`last_email_sent_at`, `email_send_count`, `last_share_opened_at` -- `supabase/migrations/20260916160000_invitation_delivery_and_rate_limit.sql`) and two new organiser-only RPCs (`record_invitation_email_sent()`, called by the `send-invitation-email` Edge Function ONLY after Resend accepts the send; `record_invitation_share_opened()`, called by the client ONLY after a non-cancelled native Share). `list_care_space_invitations()` was redefined (shape-only) to surface these. `CareCircleScreen.tsx`'s `DeliveryActions` now derives `emailed`/`shared` directly from the invitation object's own fields -- no local persisted state at all any more; `App.tsx`'s prior `recordInvitationDelivery()`/`LocalCareSpaceState.invitationDeliveryStatus` were removed as genuinely superseded, not merely deprecated in place. This survives app restart, reinstall, and a different device/session reading the same row, proven directly by a pgTAP test that reads `list_care_space_invitations()` after the state-recording calls, exactly as a second device would.

**2. A real Postgres transactional-semantics bug was found and fixed while implementing rate limiting for `resolve_invitation_by_code()`.** The first draft incremented a counter and then, on a wrong guess, raised "not found" -- but Postgres rolls back an ENTIRE statement's effects when it raises uncaught, including a counter increment performed earlier in the SAME function call. This silently no-opped the rate limiter for exactly the case it exists to catch (repeated wrong guesses). Fixed by splitting the throttle check into a genuinely separate RPC, `record_invitation_code_attempt()` (no arguments, touches only the counter, called by the client BEFORE `resolve_invitation_by_code()` -- see `src/careCircle.ts`'s `resolveInvitationByCode()`), so it commits independently as its own transaction regardless of what the following lookup call does. A second real bug, found by the pgTAP test written to prove this: the throttle exception initially used SQLSTATE `P0004`, which collides with Postgres's own reserved `assert_failure` code -- one of the two SQLSTATEs `WHEN OTHERS` explicitly does not catch, silently breaking exception handling around it. Fixed by using the plain default (P0001) like every other custom raise in this codebase. The limiter itself: a small table (`invitation_code_attempts`, no client-readable/writable RLS policies at all -- only the SECURITY DEFINER functions can touch it), 10 attempts per rolling 5-minute window per account, chosen and documented (generous enough that no genuine typo-correcting human is ever blocked; tight enough that automated guessing against the ~1.1 trillion-value code space is not economically useful).
