4. SUPABASE STORAGE CHANGES
------------------------------------
New private bucket `document-attachments` (public=false, 25MB file size
limit). Path convention: "{care_space_id}/{record_id}/{attachment_id}-
{safe filename}" -- stable IDs identify ownership; the filename suffix
is for human readability only and is never itself a security boundary.
Four storage.objects RLS policies (select/insert/update/delete) gate on
the existing can_access_care_space_records(care_space_id, 'documents',
read-or-write) -- the same domain-grant decision every record already
uses. No service-role key reaches the client at any point; all
upload/download happens through the authenticated user's own session
plus RLS.

5. ATTACHMENT ARCHITECTURE
------------------------------------
Two representations now exist, deliberately, side by side:
- record_attachments (new): durable, independently-RLS-protected cloud
  metadata with its own upload_status lifecycle (pending/uploaded/
  failed), narrow security-definer RPCs (upsert_record_attachment,
  mark_attachment_upload_status, remove_record_attachment) so an
  "uploading..." status tick never has to go through the generic record
  outbox's conflict-merge machinery meant for user edits.
- records.attachment_manifest (existing, Phase 7, unchanged): the
  local-first convenience mirror. Since its own payload builder already
  spreads every attachment field except uri, the two new client-side
  fields (storageObjectPath, uploadStatus) flow through it with zero
  changes needed to that existing sync code.
RecordAttachment.uri (src/types.ts) is now optional, reflecting reality:
a record pulled fresh on a second device genuinely has no local file
until that device downloads its own copy.

6. UPLOAD/OFFLINE ARCHITECTURE
------------------------------------
src/attachments.ts's queuePendingAttachmentUploads(careSpaceId, record):
for a document record, uploads every attachment not yet marked
'uploaded' -- persists metadata via RPC, uploads bytes (the local Expo
File object passed directly to Supabase Storage, since it implements
Blob), then marks uploaded ONLY on genuine success. Any failure at any
step leaves the attachment 'pending' for a later retry; nothing here
ever marks a file uploaded before it is. Client-generated attachment IDs
(matching records.id's own pattern) make a retried call converge rather
than duplicate, both for the metadata RPC (upsert on conflict) and the
byte upload (upsert:true).
HONEST LIMITATION: this function is written and unit-tested but not yet
called from anywhere in the app (see item 25). A document added today
still only gets a local-device copy, exactly as before this phase --
Phase 16 did not change what happens when a user adds a document today,
only what the CODE IS CAPABLE OF once Phase 17 calls it.

7. SECOND-DEVICE BEHAVIOUR
------------------------------------
A REAL, PRE-EXISTING BUG WAS FOUND AND FIXED (not merely investigated
this time): src/recordSync.ts's localRecordFromRow() used to reconstruct
a pulled record's attachments from ONLY whatever the pulling device
already had locally -- always empty on a fresh device -- never from the
server's own attachment_manifest, even though that metadata was sitting
in Supabase the whole time. It now builds attachments from the
authoritative server manifest, overlaying a local uri only where the
SAME device already has a copy under that attachment id. Confirmed by
two tests in tests/record-sync.test.ts (one updated from asserting the
old buggy behaviour to the correct one; one new test proving THIS
device's own local file survives its own create-then-echo round trip).
This makes the DATA side of "second device discovers the attachment"
true today, independent of whether Phase 17 has built a way to open it
yet.

8. DOCUMENT-VIEW BEHAVIOUR
------------------------------------
src/attachments.ts's openAttachment(attachment): prefers this device's
own local copy; otherwise requests a short-lived signed URL (the bucket
is private -- no permanent public URL exists), downloads to a scratch
cache directory, then hands the file to the native share/open sheet via
the newly added expo-sharing dependency -- no custom PDF/image renderer
was built, per the brief's own instruction. Every failure mode (missing
local copy, cloud-only file not yet uploaded, download failure, sharing
unavailable) resolves to a friendly message, never a throw/crash.
HONEST LIMITATION: not yet wired to any button in the UI (Phase 17).

9. RECORD-LINK SCHEMA AND SEMANTICS
------------------------------------
record_links: id, care_space_id, source_record_id, target_record_id,
link_type ('related_to' | 'action_for' -- both already existed in the
pre-existing RecordLink TypeScript shape, so nothing was renamed),
created_by_membership_id, created_at, deleted_at. A partial unique index
on (source, target, type) where not deleted makes creation idempotent
without a separate receipts table. Both records must belong to the same
care space -- enforced in create_record_link() by looking each record up
scoped to the caller-supplied care_space_id; a cross-space attempt is
rejected outright (proven by pgTAP). No direct table writes are
permitted (RLS has no insert/update/delete policy) -- only the
security-definer RPCs.

10. BIDIRECTIONAL PRESENTATION
------------------------------------
One stored row, read from either side: list_record_links(record_id)
returns every OTHER record linked to/from the one passed in, with a
direction ('outgoing'|'incoming') computed relative to that record --
proven by pgTAP (the document sees the appointment as outgoing; the
SAME row shows the document from the appointment's side as incoming).
No duplicate reverse row is ever created.
HONEST LIMITATION: RecordDetail does not yet render this (Phase 17) --
the query and its filtering are ready; no screen calls it yet.

11. LINKED-TASK WORKFLOW
------------------------------------
No new task-creation mechanism was built -- by design. The existing
RecordEditor.save() -> onSave(record) -> host onSaveRecord chain (used by
every "Add" button today) is exactly what a document-driven task would
call; create_record_link(..., 'action_for') is the only new piece
needed to connect the two. This was confirmed architecturally, not
executed end-to-end in a UI flow yet, since that flow doesn't exist
until Phase 17 builds the "Does anything need doing?" prompt.

12. EXPIRY BEHAVIOUR

the document, structurally isolated from a linked task's own dueDate.
No automatic task was created from expiry, and none will be unless the

HONEST LIMITATION: nothing currently CALLS remove_record_attachment or

18. MULTI-PERSON ISOLATION
------------------------------------
Every new RLS policy and RPC scopes strictly by care_space_id, mirroring
every existing Phase 7/15 pattern exactly. Cross-care-space rejection is
proven by pgTAP at three separate layers: record_links creation (a
different organiser's care space cannot link Beauty's records),
record_attachments (a different care space's member cannot attach a
file to, or even read attachment metadata for, another space's record),
and storage.objects (a different care space's member cannot upload into
or read another space's document path).
