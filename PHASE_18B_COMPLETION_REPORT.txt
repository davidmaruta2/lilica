4. MEMBERSHIP/AUTH DECOUPLING DESIGN: a Lilica account (live auth

   identity) are now separable. care_space_memberships.id is NEVER
   deleted or regenerated. Its user_id becomes nullable and is set
   to null on account deletion; membership_status gains a third
   value, 'former', alongside the existing 'active'/'revoked'.

5. SCHEMA CHANGES (one new migration,
   20260912170000_phase18b_account_deletion.sql):
   - care_space_memberships.user_id: not null -> nullable.
   - care_space_memberships.former_display_name: new, nullable text
     column, a minimal historical snapshot.
   - care_space_memberships.membership_status check constraint:
     ('active','revoked') -> ('active','revoked','former').
   - New consistency constraint: former <=> user_id null AND
     former_display_name set; not-former <=> user_id set.
   - care_spaces.bootstrap_owner_id: not null -> nullable (the
     second blocker found in item 3).
   - protect_membership_identity() trigger extended: user_id may now
     transition from live to null exactly once; never reassigned to
     a different live user; never re-attached once detached.
   - Two new functions: delete_my_account(), resolve_membership_
     identities(uuid[]).
   - account_deletion_precheck() and export_my_data() are completely
     UNCHANGED -- reused exactly as Phase 18A shipped them.

6. HISTORICAL SNAPSHOT DESIGN: former_display_name captures ONLY
   the caller's current profiles.display_name at the moment of
   deletion (or "Former member" if none) -- never an email, never a
   login identity, never anything else from auth.users. Data
   minimisation per the brief's own instruction (section 6).

7. BACKFILL BEHAVIOUR: none needed or performed. Every EXISTING
   membership already has a live user_id and membership_status of
   'active' or 'revoked' -- the new 'former' state and its snapshot
   are only ever produced going forward, by delete_my_account()
   itself, from authoritative live data at the moment of deletion.
   No inference, no fabricated identity, per section 42.

8. account_deletion_precheck() CHANGES: none. Already did exactly
   what the brief asks (sole-active-organiser detection, returning
   enough information -- care_space_id/name/blocking -- for the UI
   to explain a blocker). Reused, not bypassed or replaced.

9. SECURE SERVER DELETION MECHANISM: delete_my_account(), a single
   `security definer` Postgres function. This project has no
   separate Edge Function/service-role backend (a mobile client
   talking directly to Supabase) -- a security-definer function
   scoped to exactly this one operation is the narrowest secure
   mechanism available, and the standard pattern for self-serve
   deletion in that architecture. No service-role credential, admin
   credential, or privileged secret is ever exposed to the client.
   Target is derived exclusively from auth.uid() -- never a
   caller-supplied id, so a caller can only ever delete themselves.

10. EXACT DELETION SEQUENCE (as implemented, all in one Postgres
    transaction):
    1. Require authentication (auth.uid() not null, role
       'authenticated').
    2. Idempotency check: if the identity no longer exists in
       auth.users, return successfully as a no-op.
    3. Re-run the sole-organiser check server-side; refuse with a
       plain-language message naming the specific care space if
       blocked.
    4. Snapshot + detach every membership the caller holds (former_
       display_name, membership_status='former', user_id=null).
    5. Detach care_spaces.bootstrap_owner_id the same way.
    6. Revoke the caller's own still-pending SENT invitations only.
    7. Delete the auth.users row (profiles cascades away via its
       existing Phase 5 on-delete-cascade FK).

11. SOLE-ORGANISER PROTECTION: identical rule/check to
    account_deletion_precheck() and Phase 15's leave_care_space()/
    remove_member(). Re-run server-side inside delete_my_account()
    itself -- never trusts the client-side precheck alone. Blocked
    with a message naming the exact care space.

12. MULTI-ORGANISER BEHAVIOUR: if a second active organiser already
    exists in every space the caller organises, deletion proceeds
    cleanly. Proven in pgTAP: David deletes after Sarah is promoted
    to co-organiser of Beauty -- Beauty, its records, documents,
    links and history all survive untouched; David loses all future
    access.

13. MEMBERSHIP STATE AFTER DELETION: id unchanged; user_id null;
    membership_status='former'; former_display_name populated;
    every existing access check (already requiring 'active') denies
    it access automatically -- zero new RLS logic needed.

14. PROFILE DELETION/DETACHMENT: the live profiles row is removed
    via the EXISTING profiles.id references auth.users(id) on
    delete cascade constraint (Phase 5) -- not duplicated with a
    second explicit delete. Supported people (a wholly separate
    identity/table) are never touched by this function at all --
    proven implicitly by every surviving-data assertion in pgTAP.

15. AUTH DELETION: delete from auth.users where id = caller_id, the
    final step, only after every detach/snapshot/revoke step above
    has already succeeded in the same transaction.

16. SHARED-RECORD RETENTION: proven directly in pgTAP -- an

17. OCCURRENCE RETENTION: occurrences reference membership.id, never

18. ASSIGNMENT HANDLING: proven in pgTAP -- an assignment made to

19. ACTIVITY ATTRIBUTION: no activity-log table exists in this

20. DOCUMENT RETENTION: proven in pgTAP -- a document record and its

21. ATTACHMENT RETENTION: same as above -- record_attachments rows

22. RECORD-LINK RETENTION: proven in pgTAP -- a document-to-

23. INVITATION HANDLING: the deleting user's own still-PENDING sent

28. RETRY/IDEMPOTENCY: proven in pgTAP -- calling delete_my_account()

29. EXPORT ARCHIVE IMPLEMENTATION: per direct product-owner decision

    item 43 below), NOT a single .zip. Instead: data.json plus one
    downloaded file per authorised, available document, organised
    into documents/<care space>/<safe filename>, offered
    INDIVIDUALLY through the native share sheet (each with its own
    Share button in the UI) rather than as one combined archive.

30. data.json STRUCTURE: unchanged from Phase 18A's export_my_data()
    server shape (profile, careSpaces[] each with records/
    attachments/recordLinks), with each attachment gaining two
    client-added fields: exportPath (e.g.
    "documents/Beauty/Hospital letter.pdf") and fileAvailable
    (true/false). Never includes storageObjectPath, a signed URL,
    an auth token, or any credential -- verified directly in tests.

31. ACTUAL DOCUMENT FILE EXPORT: for each attachment the (unchanged)
    export_my_data() RPC already authorised, the client separately
    queries record_attachments directly (its own existing SELECT
    RLS re-scopes this to exactly the same authorisation) for that
    attachment's storage_object_path, then downloads the CURRENT
    cloud file via a short-lived signed URL -- never a possibly-
    stale local device copy, per the brief's own explicit
    instruction (section 30).

32. PERMISSION FILTERING: happens at two independent layers before
    any byte is ever fetched. export_my_data()'s own domain-grant
    filter decides which attachment metadata even appears in the
    export (a restricted document's id never reaches the client at
    all); the Storage bucket's own RLS (Phase 16, unchanged)
    independently re-checks the same domain-grant decision before
    serving any byte. No document is ever downloaded first and
    filtered after.

33. MULTIPLE-CARE-SPACE EXPORT: unchanged, already correct in Phase
    18A's export_my_data() -- each care space's records/attachments/
    links are filtered independently through that membership's own
    domain grants; an organiser role in one space confers no
    authority in another.

34. MISSING-FILE HANDLING: a legacy attachment with no storage path,
    one not yet marked 'uploaded', or one whose signed-URL download
    fails, is marked fileAvailable:false and skipped -- the export
    completes for everything else, never aborts, never fabricates
    bytes. The UI reports how many documents, if any, were skipped.
