4. INVITATION-CODE IMPLEMENTATION
   `care_space_invitations.invite_code` -- one additive column, NOT a
   new table, NOT a second invitation record. 8 characters, an
   unambiguous alphabet (`ABCDEFGHJKMNPQRSTUVWXYZ23456789` -- no 0/O,
   1/I/L), generated server-side by `generate_invitation_code()`
   (retries on collision -- checked, not merely assumed unique given
   the alphabet size), unique, case-insensitive at resolution time
   (`resolve_invitation_by_code()` normalises via `upper()` and strips
   non-alphanumerics, so `abcd-1234` and `ABCD1234` resolve identically),
   expires/revokes with the invitation (no independent lifecycle),
   cannot be resolved once the invitation leaves 'pending', cannot
   alter role or domain grants (the preview it returns is read-only;
   acceptance reads role/domains from the invitation row itself,
   unchanged), and does not bypass the invited-recipient restriction
   (proven directly by pgTAP -- see item 14).
   Displayed grouped as `ABCD-1234` (client-side formatting only; the
   database stores one plain 8-character string).

8. INVITATION-CREATED VS PENDING-INVITATION UX FIX
   Root cause (unchanged from the earlier, narrower brief that first
   raised this the same day): the "Invitation created" panel and the
   Pending Invitations list were two independent, unfiltered views of
   the SAME underlying `invitations` array, so a just-created
   invitation appeared in both at once. Fixed by excluding the
   just-created invitation's id from the Pending list's own filter
   while its creation panel is showing, and closing that panel
   automatically the moment a REAL success (email accepted by Resend,
   or a non-cancelled share) occurs -- at which point the SAME
   invitation reappears exactly once in Pending, truthfully labelled.
   Dismiss closes the panel without recording any delivery status,
   so the invitation reappears as "Not sent yet." rather than being
   lost. Truthful delivery state (`invitationDeliveryStatus`) is
   PERSISTED per device via a new optional field on the existing
   `LocalCareSpaceState`, saved through the exact same
   `JSON.stringify(state)` AsyncStorage path every other local-only UI
   truth (e.g. `allSetDismissed`) already uses -- genuinely NOT a new
   persistence mechanism, and genuinely NOT a database column (the
   server itself has no delivery-state column at all -- a real,
   honestly-named architectural gap this works around at the client
   level rather than papering over).
