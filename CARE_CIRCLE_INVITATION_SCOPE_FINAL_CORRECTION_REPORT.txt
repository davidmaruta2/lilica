LILICA - FINAL CARE CIRCLE INVITATION SCOPE CORRECTION
Completion report, 15 September 2026

1. WHY THE REAL Invite someone UI ONLY OFFERED MAGGIE
Traced the complete client path as instructed. The checkbox section
itself (App.tsx's organiserEligiblePeople -> CareCircleScreen's "Who can
they help with?") is implemented correctly and was already proven, in
isolation, to render both people once given a correct list. The real
defect is in HOW that list gets populated: organiserEligiblePeople is
filtered from each care space's local `role` field, and that field was
populated ONLY by a single reconnectCareSpaces() call fired once per
signed-in session, with no retry. A freshly-bootstrapped care space
(exactly David's own Maggie and Ben, created at his own onboarding) has
NO role set at all until that one background call both fires and
succeeds. If it hadn't completed yet (or had ever failed) by the time
"Invite someone" was opened, the multi-person selection silently never
appeared for the rest of that session -- with no way to recover short of
restarting the app. This is proven directly, not asserted: tests/care-
circle-invite-scope-final-correction.test.tsx's first test reproduces
the exact starting condition (role undefined on both spaces immediately
after bootstrap).

2. EXACT CLIENT FIX
App.tsx now re-runs the existing, unmodified reconnectCareSpaces()/
integrateReconnectedCareSpaces() pair every time Care Circle is opened
(the same already-established refresh-on-open pattern this codebase
already uses for members/invitations), not only once at session start.
No new RPC, no new client function, no change to CareCircleScreen's own
rendering logic (already correct) -- only when its underlying data
gets refreshed.

3. PROOF DAVID NOW SEES MAGGIE + BEN AS SELECTABLE
