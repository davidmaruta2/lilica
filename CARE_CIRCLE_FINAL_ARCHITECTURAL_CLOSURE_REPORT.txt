CODE SECURITY
################################################################

9. CODE ENTROPY/FORMAT UNCHANGED

10. RATE-LIMIT ARCHITECTURE
    A small, additive, database-backed sliding-window counter --
    `invitation_code_attempts` (user_id primary key, window_start,
    attempt_count). No Redis, no external infrastructure. A REAL
    Postgres transactional-semantics bug was found and fixed while
    building this: the first draft incremented the counter and THEN,
    on a wrong guess, raised "not found" inside the SAME function call
    -- but Postgres rolls back an entire statement's effects on an
    uncaught exception, including work done earlier in that same call.
    This would have silently no-opped the limiter for exactly the case
    it exists to catch (repeated wrong guesses). Fixed by splitting the
    throttle check into its own RPC, `record_invitation_code_attempt()`
    (no arguments, touches only the counter), called by the CLIENT
    first, strictly before `resolve_invitation_by_code()` -- see
    `src/careCircle.ts`'s `resolveInvitationByCode()`. Each call
    commits independently, so a later "not found" in the SEPARATE
    resolve call cannot undo an already-committed increment. A SECOND
    real bug, found by the pgTAP test written to prove this: the
    throttle exception initially used SQLSTATE `P0004`, which collides
    with Postgres's own reserved `assert_failure` -- one of the two
    codes `WHEN OTHERS` explicitly does not catch, breaking exception
    handling around it silently. Fixed to use the plain default (P0001)
    like every other custom raise in this codebase.

11. THRESHOLD/WINDOW
    10 attempts per rolling 5-minute window, per authenticated account.
    Chosen and documented (not arbitrary): generous enough that a real
    person correcting typos is never blocked (no genuine user mistypes
    a code 10 times in 5 minutes); tight enough that automated
    guessing against the ~1.1 trillion-value code space (32^8) is not
    economically useful (10 guesses/5 min = ~2,880/day).

12. SERVER ENFORCEMENT
    `invitation_code_attempts` has RLS enabled and FORCED, with ZERO
    policies defined -- not even the owning user can read or write it
    directly. Only the two SECURITY DEFINER functions
    (`record_invitation_code_attempt()`, and `resolve_invitation_by_
    code()` for the lookup itself) can touch it, since RLS does not
    apply to a SECURITY DEFINER function's own internal access as its
    defining role. Cannot be bypassed by clearing local storage or
    reinstalling -- the counter lives entirely server-side, keyed by
    the authenticated account's own `auth.uid()`.

13. PREVIEW FIELDS RETURNED
    Unchanged from the prior pass, re-confirmed by direct reading:
    `resolve_invitation_by_code()` still returns only `id`,
    `care_space_name`, `invited_by_display_name`, `role`,
    `granted_domains` -- never `invitee_email`, never `care_space_id`,
    never a membership id, never a record/contact/document, never
    another Care Circle member's information.

14. INVALID-CODE BEHAVIOUR
    Unchanged from the prior pass, deliberately preserved rather than
    collapsed to one generic message: "We could not find an active
    invitation with that code" (genuinely nonexistent/malformed) versus
    "This invitation is no longer active" (a real invitation the caller
    already possessed the code for, now revoked/accepted/declined/
    expired) -- the distinction reveals only that THIS specific code
    once existed, never who it belonged to or what care space it names,
    so it does not create a useful enumeration oracle. This was this
    pass's own explicit judgement call, stated rather than silently
    assumed: the immediately-prior brief's own section 12 permits this
    exact distinction ("where the server can safely distinguish it").
    A THIRD, new outcome added this pass: "Too many attempts. Please
    wait a few minutes and try again." -- distinct from both, so a
    throttled user is never confused with either a wrong code or a
    genuinely inactive one.

15. IDENTITY/ACCEPTANCE ENFORCEMENT UNCHANGED
    `accept_invitation()` was NOT touched by this pass. Proven directly,
    not merely re-asserted: a new pgTAP test
    (`invitation_code_rate_limit.test.sql`) resolves a real code as an
    unrelated account and then calls `accept_invitation()` against the
    resolved id, confirming it is STILL refused ("Invitation not
    found") -- completely unaffected by whether rate limiting was
    involved in reaching that id.

16. ABUSE/SECURITY TESTS
    `supabase/tests/database/invitation_code_rate_limit.test.sql` (9
    assertions, all passing): a normal valid lookup succeeds; ordinary
    typo/retry (3 wrong guesses then the real code) remains practical
    and unblocked; 7 more attempts reach the threshold exactly without
    throttling; the 11th attempt in the same window is throttled, even
