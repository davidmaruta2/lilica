12. EXISTING DELETE CAPABILITY PRESERVED
    `delete_care_space()`'s checkbox confirmation
    (`RemoveCareSpaceConfirm.tsx`), irreversible warning, storage/document
    cleanup, multi-care-space handling (`removableCareSpaces` in
    App.tsx/Privacy & data), and its own full cascade-delete correctness
    are all completely unchanged and still pass every one of their
    original tests. Nothing about the sole-organiser path regressed.

13. SOLE-ORGANISER BEHAVIOUR
    Deletes immediately, exactly as before - server re-queries the real
    organiser count itself every time (never trusts a client-supplied
    flag, per section 15's explicit instruction), verified directly by
    pgTAP.

14. MULTI-ORGANISER CONSENT ARCHITECTURE
    New `care_space_deletion_requests`/`care_space_deletion_approvals`
    tables - deliberately `ON DELETE CASCADE` (ephemeral workflow state,
    not permanent audit, per section 12's "keep the model as simple as
    possible"). `request_care_space_deletion(target_care_space_id,
    deletion_reason)`: a sole organiser is deleted immediately (no request
    row ever created); with multiple active organisers, creates a request
    and the requester's own approval counts automatically.

15. REQUEST BEHAVIOUR
    Only an active organiser may request; an optional `reason` (`
    care_no_longer_required`/`supported_person_requested`/`other`) is
    recorded as contextual/audit metadata only - never presented or
    treated anywhere as legal consent evidence (section 16's explicit
    instruction). A second request against a care space that already has
    one pending resolves to the SAME existing request (unique constraint
    on `care_space_id`), never a duplicate.

16. APPROVAL BEHAVIOUR
    `approve_care_space_deletion(request_id)`: only an active organiser of
    that care space may approve; a duplicate approval by the same
    organiser is silently harmless (unique constraint on
    `(request_id, membership_id)`, proven directly by pgTAP: approving
    twice never double-counts); once every currently-active organiser has
    approved, the function performs the ACTUAL deletion itself, via the
    exact same, unmodified `delete_care_space()` machinery (a trusted,
    narrow, transaction-scoped bypass flag - the same established pattern
    already used for the activity-immutability trigger - lets this one
    internal caller through the new multi-organiser gate).

17. DECLINE BEHAVIOUR
    `decline_care_space_deletion(request_id)`: ANY active organiser (not
    only the requester) may decline; the request row is deleted outright -
    a later attempt requires a genuinely new request (section 14's
    explicit instruction against "ambiguous half-approved" state).

18. CANCELLATION BEHAVIOUR
    `cancel_care_space_deletion(request_id)`: only the ORIGINAL requester
    may cancel their own pending request - a distinct, narrower authority
    than decline's "any organiser", proven directly by pgTAP (a different
    organiser attempting to cancel someone else's request is rejected).

19. FINAL DELETION TRANSACTION
    Identical, unmodified cascade sequence as the original
    `delete_care_space()` (occurrence_versions -> mutation receipts ->
    assignments -> activity -> links/attachments -> occurrences ->
    recurrence -> records -> contacts/invitations -> domain grants ->
    memberships -> supported_people -> care_spaces), with exactly one
    addition: `care_space_deletion_requests` is now explicitly deleted
    before memberships (a real bug found only by running this exact
    deletion - see item 50 below).

20. STORAGE/DOCUMENT CLEANUP
    Completely unchanged - `deleteCareSpace()` (src/careSpaces.ts) still
    fetches every attachment's storage path before calling the RPC and
    best-effort removes them afterward, queuing failures via the existing
    Phase 18 durable retry mechanism. Never touched by this task.

21. DELETE TESTS

24. ELIGIBLE-TARGET RULES

    a clear message).

25. EXISTING-MULTIPLE-ORGANISER BEHAVIOUR
    If another active organiser already exists, the departing organiser
    does not need to use `promote_to_organiser()` at all - they can simply
    call the existing `leave_care_space()` directly, which already
    correctly permits this once the organiser-count invariant is
    satisfied. No new code was needed for this case specifically.

26. ORIGINAL-ORGANISER LEAVE BEHAVIOUR

    deliberately AFTER the existing organiser-count invariant (the more
    fundamental blocker, checked first so a sole organiser who also
    happens to be the commercial owner sees the more useful message): an
    organiser who is also the care space's `commercial_owner_id` cannot
    leave until they transfer commercial ownership away from themselves,
    using Phase 21B's own existing, completely unmodified
    `transfer_care_space_commercial_ownership()`. No second billing-owner
    model was created.

27. COMMERCIAL_OWNER_ID HANDLING
    Reused Phase 21B's existing mechanism exactly as instructed (section
    22: "reuse the existing Phase 21B authority/mechanism... do not
    create a second billing-owner model"). Proven directly by pgTAP: David
    (sole commercial owner, now with Marion also an organiser) is still
    blocked from leaving until he transfers ownership to Marion, then can
    leave successfully.

28. HANDOFF TESTS
