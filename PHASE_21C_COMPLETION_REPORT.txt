14 September 2026


1. WHAT THIS TASK WAS

Phase 21B (billing/subscription/entitlement) was approved and implemented server-side
and client-side. Its own completion report identified one genuine remaining gap: the
server correctly rejects a gated mutation once entitlement expires, but the client UI
still let a user start a mutation flow (e.g. open the Add form) and discover only at
Save time that it couldn't be saved. Phase 21C's job was to close that gap with a
proactive, centralised, calm client-side read-only layer - explicitly NOT a billing
redesign, NOT a visual redesign, NOT permission-architecture work, and NOT Phase 22.

The approved commercial model is unchanged throughout: 60 days completely free, then
£8.99/year.


2. WHAT WAS BUILT

- Central state and gate (App.tsx): a `careSpaceCommercialStatus` value for the active
  care space, fetched via Phase 21B's own existing `getCareSpaceCommercialStatus()` RPC
  (no new RPC), refetched on care-space switch, falling back to the existing 72-hour
  offline cache when unreachable. Derives one `isReadOnly` boolean and one
  `guardMutation(action)` function - the single place every gated entry point calls
  through. A local-only (never-synced) care space is never read-only. Not-yet-loaded
  status deliberately means "not read-only" (never assume expired).

- One reusable notice component (src/components/ReadOnlyGate.tsx), two copy variants:
    OWNER: "Your free period has ended" / "Your information is safe and you can still
    view everything you've saved." / "Subscribe for £8.99/year to continue adding or
    making changes." - with a real Subscribe route into the existing, UNMODIFIED
    SubscriptionScreen.
    COLLABORATOR: "This care space is currently read-only." / "Existing information is
    still available, but new information and changes are paused until the subscription
    for this care space is active again." - no Subscribe action, no mention of the
    collaborator's own subscription, no exposure of the owner's real entitlement status
    or billing detail. Calm styling throughout - no red/alarm colours, no countdown, no
    fake scarcity; shown only in direct response to an explicit tap, never popped
    automatically.

- Five gated entry points, matching Phase 21B's own server-side mutation inventory:
    1. Home's +Add
    2. To Do's +Add
    3. Person's per-section Add links, and Key Contacts' own Add link
    4. The shared Edit trigger for an EXISTING record (RecordQuickEditor.tsx and
       FirstThingScreen.tsx) - the Edit button itself stays VISIBLE either way, never
       silently hidden, per the brief's explicit requirement; tapping it while
       read-only shows the gate instead of entering edit mode. FirstThingScreen's own
       category-create path is gated the same way as a second line of defence.
    5. Care Circle's "Invite someone" - stays visible, blocked on tap.

- Deliberately NOT independently gated: micro-actions inside an already-open editor
  (attach file, remove/relink, individual field edits, the completed toggle) - entry
  into edit mode is itself already gated; a mid-edit expiry is the rare race the
  server-rejection fallback below exists for. remove_member(), leave_care_space(),
  accept_invitation(), decline_invitation(), Account, Privacy & data, Export and every
  read/list surface are all confirmed unaffected - they were never gated server-side
  either.

- Friendly server-rejection fallback: a new `hasEntitlementHeldMutations()` read in
  src/recordSync.ts (reusing Phase 21B's own existing `isEntitlementHeldMutation()`
  predicate - no new state, no new store) drives one small, dismissible, non-modal
  notice in App.tsx for the rare remaining race where a mutation is rejected by the
  server after the proactive gate has already passed. Calm, translated copy only -
  never a raw Postgres/RPC error.

- The server remains the sole, final authority throughout. Nothing about Phase 21B's
  server enforcement, RPCs, entitlement state machine, or RevenueCat/webhook
  architecture was touched, redesigned, or weakened.
