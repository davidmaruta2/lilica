4. FIRST CLOSE THE PHASE 17 DOCUMENT-CLEANUP GAP
================================================================

Before claiming mature deletion/account lifecycle, close the known Phase 17
limitation:

today:

document record deletion
→ canonical tombstone is queued correctly

but:

cloud file/link cleanup
→ best-effort fire-and-forget
→ may be stranded permanently if deletion occurs offline or cleanup fails.

This is not acceptable as the final privacy/deletion model.

Implement the smallest durable, idempotent cleanup mechanism compatible with
the existing Phase 7/16/17 architecture.

Requirements:

- an offline document deletion may queue cloud cleanup;
- app restart must not forget pending cleanup;
- reconnect retries it;
- repeated retry must not duplicate or corrupt cleanup;
- record tombstone remains canonical;
- linked independent records/tasks survive;
- relevant record_links are tombstoned/removed safely;
- record_attachment metadata is removed/tombstoned safely;
- Storage object is deleted safely;
- already-missing file is treated idempotently;
- failure remains retryable;
- care-space isolation enforced;
- revoked/unauthorised clients cannot use cleanup to delete others' files.

Do NOT redesign record deletion.

Do NOT build a giant generic job system if a small durable cleanup queue/state
is sufficient.

Explicitly test:

offline delete
→ restart
→ reconnect
→ cleanup completes exactly once.

This correction is part of Phase 18 because deletion/privacy lifecycle cannot
be considered complete otherwise.

10. DATA EXPORT - USER PURPOSE
================================================================

An authenticated user should be able to obtain a copy of the data they are
currently entitled to export.

Export must be clear about:

- whose data is included;
- which care spaces are included;
- what file format is produced;
- whether documents/files are included;
- generation time/date.

Do not silently export information from care spaces the user cannot access.


================================================================
11. EXPORT SCOPE
================================================================

Design export around CURRENT authorised visibility.

A user may have:

- their own account/profile data;
- memberships in multiple care spaces;
- organiser access in one space;
- contributor access in another;
- viewer access elsewhere.

Export must honour current permissions.

Do not let export become a security bypass.

A member denied Financial cannot obtain Financial records through Export.

A member denied Documents cannot obtain document records/files through Export.

Server-side permission enforcement remains authoritative.


================================================================
12. EXPORT FORMAT
================================================================

Use a portable, understandable format.

At minimum produce structured machine-readable data such as JSON and/or an
appropriate human-readable package where practical.

The export should preserve:

- stable IDs where useful;
- record type;
- dates;
- statuses;
- relationship/link information;
- assignment attribution;
- activity/history where authorised;
- relevant metadata.

Do not expose internal secrets/tokens.

Do not include:

- auth tokens;
- service keys;
- private signed URLs;
- database credentials;
- device push tokens unnecessarily.


================================================================
13. DOCUMENTS IN EXPORT
================================================================

Phase 16/17 introduced secure documents and real persisted links.

Where authorised, export should include:

- document record metadata;
- attachment metadata;
- actual document bytes where safe/appropriate;
- record-link relationships;
- linked task relationships.

Do NOT export temporary signed URLs as the document.

Do not make document export dependent on the originating device.

Cloud-stored authorised files should be exported from the authoritative cloud
location.

Reference-only metadata must still export correctly if the historical file
itself is unavailable.


================================================================
14. RECORD LINKS IN EXPORT

================================================================
19. CLEAR LOCAL DATA
================================================================

Provide or implement the approved:

Clear data from this device

behaviour if consistent with current product architecture.

Make consequences explicit.

It affects local state only.

It must NOT:

- delete cloud records;
- delete cloud documents;
- delete the account;
- remove other care-circle members.

Require confirmation.

Before clearing, inspect:

- pending record mutations;
- pending document uploads;
- pending document cleanup.

If any exist:

warn appropriately.

Do not silently discard unsynced work.


================================================================
20. LOCAL DOCUMENT CACHE
================================================================

Downloaded/cached document bytes are particularly sensitive.

Clear local data should remove appropriate local downloaded copies.

It must NOT remove authoritative cloud files.

Be especially careful with:

LEGACY LOCAL-ONLY FILES

If the device possesses the only remaining copy of an older attachment that
has never successfully uploaded to cloud:

do NOT silently destroy it.

Warn clearly.

The user must understand that clearing local data could permanently lose that
file if no cloud copy exists.


================================================================
21. PENDING DOCUMENT UPLOAD DURING CLEAR
================================================================

If a file has:

local copy
+
pending cloud upload

then clearing local data could destroy the only upload source.

Do not permit silent destructive clearing.

Require:

- successful upload first;
- explicit informed discard;
- or another safe approved resolution.

Do not falsely claim the file is safely backed up.


================================================================
22. PENDING DOCUMENT CLEANUP DURING CLEAR
================================================================

If a deleted document still has pending cloud cleanup:

do not simply discard the cleanup instruction from local state and strand the
cloud object forever.

Either:

- complete cleanup first;
- persist cleanup server-side/durably enough to survive local clearing;
- or explicitly block/warn according to the architecture implemented in
  section 4.

This must be tested.


================================================================
23. LEAVE A CARE SPACE
================================================================

A normal member should be able to leave where permitted.

Leaving one care space means:

- membership becomes inactive/left according to canonical model;
- access ends;
- assignments/history remain attributable;
- other care spaces remain intact;
- account remains intact.

Do not make Leave equivalent to Delete account.


================================================================
24. SOLE ORGANISER SAFETY
================================================================

Do not allow a sole organiser to leave/delete themselves in a way that
silently strands a care space.

Before destructive account/care-space actions, determine:

- is the user the sole organiser?
- are there other active organisers?
- does current architecture support ownership transfer/succession?

If not:

block unsafe action and explain the next required step.

Do not invent an unsafe ownership transfer.

================================================================
26. ACCOUNT DELETION - CORE PRINCIPLE
================================================================

Account deletion must be real.

It is NOT:

- sign out;
- deactivate UI;
- hide profile;
- clear local cache.

A user requesting account deletion expects their Lilica account to be removed
according to the implemented retention/lifecycle policy.

This has consequences across:

- auth user;
- profile;
- memberships;
- invitations;
- assignments;
- activity attribution;
- records they created;
- care spaces they organise;
- record links;
- document attachments;
- cloud Storage;
- device tokens;
- reminders;
- local data.

Model this carefully.


================================================================
27. DO NOT DELETE SHARED CARE DATA JUST BECAUSE ONE USER LEAVES
================================================================

A record created by Sarah in Maggie's shared care space does not necessarily
belong solely to Sarah.

If Sarah deletes her account:

do NOT automatically erase Maggie's care record if other authorised members
still rely on it.

The same applies to:

- documents;
- document attachment files;
- linked tasks;
- record_links;
- activity.

Shared care-space data belongs to the care space according to existing
architecture.

Preserve historical attribution safely.


================================================================

================================================================
30. SERVER-SIDE ACCOUNT DELETION
================================================================

Do not give the mobile client service-role credentials.

Consequential auth-user deletion must happen through an appropriate secured

The operation must:

- authenticate caller;
- verify they are deleting their own account;
- run lifecycle checks;
- handle memberships safely;
- remove/revoke device tokens;
- suppress future notifications;
- clean profile/account-owned data according to policy;
- delete/deactivate auth identity appropriately.

Do not trust a client-supplied arbitrary user ID.

================================================================

================================================================
36. DOCUMENT-LINK INTEGRITY AFTER DEPARTURE
================================================================

Account departure/deletion must not corrupt Phase 17 record links.

For example:

Sarah uploaded Hospital letter
and linked it to Orthopaedic appointment.

If Maggie's care space continues:

- document survives if policy says shared data remains;
- appointment survives;
- link survives;
- linked task survives;
- Sarah's active access ends;
- historical attribution is handled according to policy.

Do not sever record relationships merely because the creating user departed.


================================================================
37. LOCAL CLEANUP AFTER ACCOUNT DELETION
================================================================

After successful account deletion:

clear that account's local protected state from the device, including as
appropriate:

- account-scoped record cache;
- outbox;
- pending attachment upload state;
- pending attachment cleanup state;
- care-space cache;
- downloaded documents;
- local attachment copies;
- notification state;
- setup state;
- auth session.

Do not clear locally BEFORE server deletion succeeds in a way that prevents
recovery from a failed request.


================================================================

Support retry safely.

Do not duplicate deletion operations.
